PRD — 동시 접속 그룹 미션 서버 · 제품 명세

판 v2 · 2026-11-10 (v2: 마감 직전 제출 가드 결정 D1 반영) · 원천: 과제 PRD(사용자 제공 원문). 이 문서는 원문을 빠짐없이 옮기고 규칙 단위로 다시 정리한 것이다. 원문에 없는 해석은 [해석], 원문끼리 어긋나거나 빠진 것은 열린 질문(§11) 으로 표시했다. 기능별 HLD · LLD · SPEC · ORACLE 은 이 문서를 근거로 쓴다.

세 줄 요약

  • 매일 07:00~08:00 KST, 250만 명이 동시에 접속해 2~10명 그룹 단위로 각자 퀴즈 3문제를 순서대로 푼다. 그룹원 전원이 3문제를 풀면 그룹 성공, 08:00 에 미완료면 실패다.
  • 서버는 문제를 고르거나 채점하지 않는다. 문제은행(정답은 해시)을 내려주고 풀이 · 패스 · 부정 실패 신호를 받아 진행도 · 그룹 상태 · 랭킹을 확정하고, 그룹원에게 실시간으로 알린다.
  • 핵심 정합성은 마감 이후 미반영 · 성공 1회 기록 · 신호 유실/중복 없음 · 랭킹 일치 · 재시작 내구성이다. NFR-1 은 마감 직전 제출 가드(D1) 로 완화했다 — 08:00 이전에 클릭한 제출은 08:00:03 까지 도착하면 인정한다. 남은 충돌 · 빈칸은 §11 에서 결정한다.

1. 개요

항목 내용
제품 매일 같은 시각에 모든 유저가 동시에 접속해 그룹 미션을 수행하는 게임의 백엔드
게임 시간 매일 07:00 ~ 08:00 KST (제한시간 1시간). 모든 시각은 KST(UTC+9) 기준
미션 그룹원 각자 퀴즈 3문제를 1번부터 순서대로 푼다. 그룹원 모두가 3문제를 다 푸는 순간 그룹 성공
퀴즈 컨셉 KBS 「1 대 100」 같은 퀴즈쇼, 주관식. 분야: 시사 · 정치 · 사회 · 상식
서버의 몫 가입 · 인증 · 그룹, 문제은행 제공, 풀이/패스/실패 신호 반영, 그룹 판정, 실시간 전달, 마감, 결과 · 랭킹
클라이언트의 몫 문제 선정(무작위), 정답 판정(해시 비교), 로컬 스토리지 상태 유지, 부정행위 경고, 마감 시 제출 버튼 비활성화
범위 밖 클라이언트 · 관리자 화면, 결제, 보상 지급, 그룹 탈퇴와 이동

1.1 목표

  • G1 일일 참가자 250만 명이 같은 시각에 접속하는 게임을 처리한다.
  • G2 정합성 조건(§9.2)을 지킨다.
  • G3 그룹원의 진행 상태가 다른 그룹원에게 실시간으로 보인다.
  • G4 클라이언트 개발자가 개발 문서와 API 정의만으로, 서버 개발자에게 묻지 않고 개발을 시작할 수 있다.

2. 용어

용어 정의
진행도 유저가 그날 푼 문제 수 0~3. 줄어들지 않는다. 미션 시작 전(07:00 이전의 모든 유저 · 접속하지 않은 유저)은 -1 — 현황판에는 0 으로 표기
미션 시작 그 날짜 07:00 이후 문제은행을 한 번이라도 받은 것. 07:30 에 처음 받으면 그때가 시작
풀이 신호 유저가 문제를 풀면 클라이언트가 보내는, 해당 문제 번호의 신호 (문제 번호 · 문제 PK · successTime · 클릭 시각)
패스 신호 하루 1번, 지금 문제를 같은 난이도의 다른 문제로 바꿀 때 보내는 신호 (문제 번호 · 넘긴 문제 PK)
실패 신호 로컬 스토리지가 빈 것을 감지한 클라이언트가 보내는 부정 실패 처리 요청
유저 미션 상태 진행 중 또는 완료. 완료 = 미션 성공(3문제 다 풂) 또는 미션 실패(부정으로 실패 처리됨). 「완료」는 판정용 내부 상태이고 유저에게 보이는 상태는 성공 · 실패 · 진행 중뿐
그룹 상태 진행 중 · 성공 · 실패
그날의 그룹원 그 날짜 07:00 이전 가입자까지만. 현황판 · 그룹 성공 조건 · 그룹 내 랭킹 · 그룹 인원 모두 이 기준
현황판 그날의 그룹원 목록. 그룹원마다 ID · 진행도(0~3) · 상태 · 랭킹을 보여 주고 랭킹순으로 정렬
지각 미션 시작 시각(07:00)보다 늦게 들어온 것. 서비스 상태가 아니라 랭킹을 정할 때만 쓴다

3. 하루 타임라인

구간 (KST) 서버 동작 유저가 보는 화면
전날 08:00 ~ 07:00 풀이 · 패스 신호 거부. 가입 받음(07:00 이전 가입자가 그날 그룹원) 직전 게임 결과(성공/실패 · 그룹 내 랭킹) + 다음 게임까지 남은 시간. 06:55 접속이면 「5분 후 게임 시작」 + 남은 시간
07:00 그날 그룹원 명단 확정(07:00 이전 가입자). 모든 유저 진행도 -1 현황판 + 1번 문제 (앱을 켜 두고 기다렸든 07:00 에 다시 접속했든 같음)
07:00 ~ 08:00 문제은행 제공(= 미션 시작), 풀이 · 패스 · 실패 신호 반영, 그룹 판정, 실시간 전달 현황판 + 다음 문제 / 본인 완료 화면 / 그룹 결과 화면
08:00 ~ 08:00:03 제출 가드(D1): 이 3초 동안 도착한 풀이 신호 중 클릭 시각이 08:00 이전인 것만 반영. 그 밖의 신호는 거부 제출 버튼 비활성화
08:00:03 유예가 끝나면 미완료 그룹 실패 확정 [해석 — D1 의 귀결]. 이후 도착 신호는 모두 거부 제출 버튼 비활성화. 그룹원 모두에게 결과(성공/실패) + 그룹 내 랭킹
08:00 ~ 다음 07:00 결과 조회 오늘 게임 결과 + 다음 게임까지 남은 시간을 둘 다

4. 상태 모델

4.1 유저 (그날 기준)

상태 진행도 유저에게 보이는 상태 들어가는 조건
시작 전 -1 (표기 0) 진행 중 [해석] 07:00 이전, 또는 그날 문제은행을 아직 받지 않음
진행 중 0~2 진행 중 07:00 이후 문제은행을 처음 받음
완료 · 미션 성공 3 성공 3번 문제의 풀이 신호가 반영됨
완료 · 미션 실패 실패 처리 시점의 값 08:00 전 다른 그룹원에게는 진행 중(그 시점 진행도로), 본인에게는 실패. 그룹 결과 확정 뒤에는 모두에게 실패 미션을 시작한 유저의 실패 신호(로컬 스토리지 빔)가 반영됨
  • 진행도는 줄어들지 않는다. 완료된 유저의 상태는 바뀌지 않는다 [해석 — 성공 뒤 실패 신호는 §11 Q7].
  • 자의로 중도 포기할 수 없다.

4.2 그룹 (그날 기준)

상태 조건 기록
진행 중 07:00 이후, 결과 미확정 —
성공 그날의 그룹원 모두가 미션 성공하는 순간 성공 판정과 완료 시각을 정확히 한 번 기록
실패 (즉시) 그날의 그룹원이 모두 완료가 되는 순간, 미션 실패가 한 명이라도 있음 (전원 부정 실패도 같음) 실패 확정도 한 번만 기록
실패 (마감) 08:00 에 아직 진행 중 (접속하지 않은 그룹원이 있으면 성공할 수 없어 여기로 온다) 한 번만 기록
결과 없음 그날의 그룹원이 1명 — 그룹이 아닌 것으로 취급, 미션을 시작할 수 없다 성공도 실패도 없음
  • 성공 · 실패가 확정되는 즉시 그룹원 전원 화면에 결과 메시지와 그룹 내 랭킹을 보내고 결과 조회 화면으로 옮긴다.

5. 기능 요구사항

id 이름 요구
FR-1 자동 참가 모든 유저는 매일 자기 그룹으로 게임에 자동 참가
FR-2 그룹 소속 유저는 서비스를 쓰는 동안 계속 특정 그룹(2~10명)에 속함. 가입할 때 기존 그룹과 새 그룹 중 하나를 고름
FR-3 게임 정보 조회 자기 그룹, 그룹원, 시작 및 마감 시각을 조회
FR-4 풀이 신호 제출 푼 문제 번호의 풀이 신호를 보내 본인 진행도에 반영. 네트워크 재시도로 같은 요청이 여러 번 와도 한 번만 반영
FR-5 실시간 진행 상태 그룹원 목록 · 각자 진행도(0~3) · 그룹 상태가 다른 그룹원에게 실시간으로 보임. 그룹이 성공하면 즉시 전원 화면에 성공 메시지와 그룹 내 랭킹. 전달 방식은 자유
FR-6 마감 처리 08:00 이후 도착한 풀이 신호는 거부하고 미완료 그룹은 실패로 확정 — 단 마감 직전 제출 가드(D1)의 3초 유예는 예외
FR-7 결과 조회 08:00 이 되면 모든 유저가 결과 화면을 봄. 성공/실패 여부와 그룹 내 랭킹(내 순위 포함)
FR-8 인증 보안상 문제가 없고 사용하는 프로토콜에 맞는 인증 체계. 가입 기능으로 가입하고 가입한 자격 증명으로 인증

5.1 가입 · 그룹 (FR-2 · FR-8)

  • R-G1 가입할 때 새 그룹(그룹명을 지정) 또는 기존 그룹(그룹명을 입력) 중 하나를 고른다.
  • R-G2 그룹명은 유일하다.
  • R-G3 그룹이 10명으로 차 있으면 11번째부터는 「그룹이 꽉 찼다」고 알려 준다.
  • R-G4 그 날짜 07:00 이전에 가입한 유저만 그날 게임에 참가한다. 07:00 이후 가입자는 다음 날부터다 [해석].
  • R-G5 그날의 그룹원 = 07:00 이전 가입자. 예: 2명 중 1명이 07:30 에 가입했으면 그날 그 그룹은 1명 그룹.
  • R-G6 그날 그룹원이 1명인 그룹의 유저는 미션을 시작할 수 없고 「그룹원이 2명 이상이어야 미션을 시작할 수 있다」는 취지로 안내한다. 그날 결과(성공 · 실패)도 없다.
  • R-G7 그룹 탈퇴 · 이동은 범위 밖이다.

5.2 미션 시작 · 문제은행 (FR-1 · FR-3)

  • R-B1 유저가 로그인하고 미션을 시작할 때 문제은행을 받는다. 07:00 이후 처음 받은 순간이 그 유저의 그날 미션 시작이다(진행도 -1 → 0).
  • R-B2 문제은행 항목: 문제 고유 PK(hash) · 난이도 · 정답 해시. 실제 정답은 내려주지 않는다.
  • R-B3 이 유저에게 이미 낸 문제(맞힌 문제 · 패스로 넘긴 문제)는 빼고 내려준다.
  • R-B4 재접속하면 문제은행을 다시 받고, 클라이언트는 로컬 스토리지에 저장된 상태로 이어서 진행한다.
  • R-B5 난이도는 1 · 2 · 3. 1번 문제 = 난이도 1, 2번 = 난이도 2, 3번 = 난이도 3.
  • R-B6 문제가 노출될 때 클라이언트가 그 번호의 난이도에 맞는 문제 중 하나를 무작위로 고른다.
  • R-B7 모든 문제는 모든 유저에게 평생 단 한 번만 제시한다(다음 날 이후에도 같은 문제 안 냄). 같은 그룹원끼리는 같은 문제가 나올 수 있다.

5.3 정답 판정 (클라이언트)

  • R-A1 클라이언트가 유저 입력을 해시해서 내려받은 정답 해시와 비교한다.
  • R-A2 정답과 유저 입력 모두 띄어쓰기 전부 제거 → 소문자 변환 → 앞뒤 공백 제거 후 해시한다. 서버와 클라이언트는 같은 정규화 · 해시 함수를 쓴다(함수는 §11 Q5).
  • R-A3 서버 DB 에는 실제 정답과 정답 해시를 따로 저장하고, 클라이언트에는 해시만 내려준다.
  • R-A4 틀리면 같은 문제를 다시 푼다(서버에 신호 없음).

5.4 풀이 신호 (FR-4)

  • R-S1 풀이 신호에는 문제 번호 · 문제 PK · successTime(맞힌 시각) · 클릭 이벤트 시각을 싣는다. 패스 정보는 싣지 않는다.
  • R-S2 서버는 문제 PK 로 이 유저에게 낸 문제를 기록해 평생 중복 금지(R-B7)를 지킨다.
  • R-S3 같은 요청이 재시도로 여러 번 와도 진행도는 한 번만 오른다(NFR-3).
  • R-S4 문제는 1번부터 순서대로 푼다 — 반영되는 신호의 문제 번호는 「현재 진행도 + 1」이다 [해석]. 이미 반영된 번호는 같은 결과로 응답하고, 건너뛴 번호는 거부한다 [해석].
  • R-S5 랭킹의 「푼 시각」은 풀이 신호가 서버에 도착한 시각이다. successTime 은 클라이언트가 바꿔 보낼 수 있어 랭킹에 쓰지 않는다.
  • R-S6 반영 즉시 그룹원에게 진행도를 전달하고(FR-5), 그룹 판정(§4.2)을 한다.

5.5 패스

  • R-P1 하루 1번, 지금 문제를 같은 난이도의 다른 문제로 바꿔 받을 수 있다(재미 요소).
  • R-P2 패스를 쓰면 클라이언트가 그 즉시 패스 API 를 호출해 문제 번호와 넘긴 문제의 PK 를 알린다. 그 번호를 끝내 못 풀어도 서버는 패스 사용 여부와 넘긴 문제를 안다.
  • R-P3 넘긴 문제는 평생 중복 금지에 포함된다.
  • R-P4 어느 문제 번호에서 패스를 썼는지가 랭킹에 반영된다(§6).
  • R-P5 하루 2번째 패스는 거부한다 [해석].

5.6 마감 (FR-6 · NFR-1)

  • R-D1 08:00 이 되면 클라이언트는 제출 버튼을 비활성화한다.
  • R-D2 마감 직전 제출 가드: 클라이언트는 클릭 이벤트 시각을 파라미터로 보낸다. 서버는 08:00 이후 3초 동안 도착한 신호도 받되, 클릭 이벤트 시각이 08:00 이전인 것만 승인한다(네트워크 지연 대비). NFR-1 · FR-6 과 어긋나는 것을 알고 「08:00 이전 제출자는 모두 인정」 원칙을 우선해 택했다 — 결정 D1(§12).
  • R-D3 유예가 끝나는 08:00:03 에 아직 진행 중인 그룹을 실패로 확정한다 [해석 — 유예 중 도착한 신호로 그룹이 성공할 수 있으므로 D1 의 귀결]. 08:00~08:00:03 사이 마지막 그룹원의 3번 신호가 승인되면 그 그룹은 성공이다.
  • R-D4 클릭 이벤트 시각은 클라이언트가 보내는 값이라 조작할 수 있지만, 그대로 믿는다 — 얻는 것이 08:00 직후 최대 3초뿐이라 동기가 약하고, 손으로 파라미터를 고치려면 3초 넘게 걸린다(D1). 랭킹은 여전히 서버 도착 시각으로 정한다(R-S5).

5.7 로컬 스토리지 · 부정 실패

  • R-F1 새로고침이나 진행 상황에 따라 같은 문제로 돌아오기 위해 클라이언트는 로컬 스토리지를 쓴다.
  • R-F2 그 날짜에 미션을 시작한 유저(진행도 0 이상)의 로컬 스토리지가 비어 있으면, 클라이언트가 서버의 실패 처리 API 를 호출한다. 서버는 그 유저를 그날 미션 실패로 처리하고 랭킹 · 그룹 판정에 반영한다. 클라이언트는 완료 화면 · 현황판으로 리다이렉트한다.
  • R-F3 브라우저 닫기 · 탭 이동 · 속성 보기(로컬 스토리지를 지울 수 있는 곳) 시도에는 「부정행위로 실패 처리될 수 있다」 경고만 준다. 실제 실패 처리는 로컬 스토리지가 빈 경우뿐이다.
  • R-F4 표시: 08:00 전에는 부정 실패 유저도 다른 그룹원에게 **실패 처리 시점까지 푼 문제 수와 「진행 중」**으로 보인다. 그룹 결과가 확정돼 모두가 현황판에 모인 뒤에는 **「실패」**로 보인다.
  • R-F5 실패 처리된 본인은 완료 화면으로 가서 현황판을 본다. 본인 상태는 「실패」이고 그룹 상태를 같이 본다.
  • R-F6 부정 실패도 「완료」로 취급한다 — 나머지 그룹원이 모두 3문제를 풀면 그 즉시 그룹 실패 확정(§4.2).

5.8 실시간 진행 상태 (FR-5)

  • R-R1 전달 대상: 그룹원 목록 · 각자 진행도(0~3, -1 은 0 으로) · 상태 · 그룹 상태.
  • R-R2 1번 문제를 제출하면 바로 2번 문제로 가고, 같은 시점에 다른 그룹원 현황판에 이 유저가 1번까지 풀었다고 표시된다.
  • R-R3 그룹 결과(성공 · 즉시 실패 · 마감 실패)가 확정되면 그 즉시 전원 화면에 결과 메시지 + 그룹 내 랭킹을 보낸다.
  • R-R4 재접속 · 늦은 접속(07:30)에는 다른 그룹원의 현재 진행도가 반영된 현황판을 준다.
  • R-R5 전달 방식(WebSocket · SSE · 폴링 등)은 자유. 메시지 형식은 기계가 읽을 수 있게 정의한다(§9.3).

5.9 결과 조회 (FR-7)

  • R-V1 08:00 이 되면 모든 유저가 결과 화면을 본다: 성공 또는 실패 + 그룹 내 랭킹(내 순위 포함).
  • R-V2 08:00 이후 ~ 다음 게임 시작 전 접속: 오늘 게임 결과와 다음 게임까지 남은 시간을 둘 다 보여 준다.
  • R-V3 결과 화면의 랭킹은 최종 상태와 일치한다(NFR-4).
  • R-V4 1명 그룹은 결과가 없다(R-G6).

6. 랭킹 규칙 (그룹 내)

위에서부터 차례로 비교한다. 앞 키가 같을 때만 다음 키를 본다.

9. 비기능 요구사항

9.1 규모

  • 일일 참가자 2,500,000명, 그룹 크기 2~10명.
  • 리소스(DB · 컴퓨팅)는 합리적인 비용 범위에서 자유. 단 구조를 효율적으로 설계하지 않고 리소스만 늘려서 해결하지 않는다.
  • 원문 숫자에서 바로 나오는 양 [해석 — 산술만, 실측 아님]:
양 값 계산
그룹 수 250,000 ~ 1,250,000 250만 ÷ 10 ~ 250만 ÷ 2
하루 최대 풀이 신호(재시도 제외) 7,500,000 250만 × 3
하루 최대 패스 신호 2,500,000 250만 × 1
1시간 평균 풀이 신호 약 2,083 건/초 7,500,000 ÷ 3,600 — 07:00 직후 몰림은 평균보다 훨씬 크다(피크 배수는 확인 필요)
동시 실시간 연결 최대 2,500,000 참가자 전원이 현황판을 켜 둔 경우

9.3 클라이언트 연동

  • 클라이언트는 모바일 앱과 웹 양쪽.
  • API 정의는 OpenAPI 처럼 기계가 읽을 수 있는 형식으로 제공하고, 실시간 전달 메시지 형식도 함께 정의한다.
  • 개발 문서에는 게임 하루 흐름에 따른 호출 순서, 에러 코드와 클라이언트 대응 방법을 담는다.
  • 완료 조건: 클라이언트 개발자가 서버 개발자에게 따로 묻지 않아도 되는 수준.

10. 기술 제약과 자유도

  • 언어 · 프로토콜 · 스토리지 · 미들웨어는 자유. 스토리지와 미들웨어는 선택 이유와 포기한 대안을 설계 문서에 적는다.
  • 실행: docker compose up 한 번으로 서버와 의존 스토리지가 모두 떠야 한다.
  • 클라우드: 실제 클라우드 리소스는 쓰지 않는다. 운영 환경에서 무엇을 추가할지는 문서로만 설명한다.
  • 범위 밖: 결제, 보상 지급 로직, 클라이언트 구현, 그룹 탈퇴와 이동.

11. 열린 질문 — 원문끼리 어긋나거나 빠진 것

설계 문서(HLD)에서 결정하고, 결정한 내용과 근거를 그 문서의 「결정과 버린 대안」에 남긴다.

id 질문 원문 근거 영향
Q1 마감 3초 유예 vs 마감 이후 미반영 — 결정됨(D1): 08:00 이전 제출자를 모두 인정하는 원칙을 우선해 3초 유예를 둔다. 그룹 마감 실패 확정은 08:00:03 (R-D3) §5.6 · NFR-1 · FR-6 —
Q2 클릭 이벤트 시각을 믿어도 되는가 — 결정됨(D1): 믿는다. 조작으로 얻는 것이 최대 3초뿐이라 어뷰징은 현실적으로 거의 없다고 본다 (R-D4) R-D2 · R-S5 —
Q3 노출됐지만 풀지도 패스하지도 않은 문제. 서버는 맞힌 문제 · 패스한 문제만 안다. 08:00 까지 못 푼 문제(또는 부정 실패 때 화면에 있던 문제)는 다음 날 다시 나올 수 있어 「평생 단 한 번 제시」(R-B7)를 어길 수 있다 R-B3 · R-B7 · R-S2 문제 중복 · 문제은행 설계
Q4 08:00 전 실시간 현황판에서 부정 실패 유저의 랭킹 자리. 「진행 중 · 그 시점 진행도」로 보여야 하는데(R-F4), 랭킹 규칙은 부정 실패를 꼴등으로 둔다(§6). 실시간 현황판의 랭킹은 어느 기준인가 R-F4 · §6 현황판 정렬 · 정보 노출
Q5 정답 해시 함수와 강도. 함수가 정해져 있지 않다. 정규화된 주관식 답은 후보가 적어 소금(salt) 없는 해시는 사전 대입으로 쉽게 풀린다. 문제별 salt 를 함께 내려줄지 R-A1~A3 · R-B2 보안 · 클라이언트 구현
Q6 지각 판정 기준. 07:00:00 에 정확히 시작할 수 있는 사람은 거의 없다. 07:00 이후 몇 초까지를 「지각 아님」으로 볼지 §6 진행도 0 동률 정렬
Q7 이미 미션 성공한 유저의 실패 신호. 3문제를 다 푼 뒤 로컬 스토리지가 비면 실패로 바꾸는가, 무시하는가 R-F2 · §4.1 그룹 판정 · 성공 1회 기록
Q8 「오늘 게임 결과」의 범위. 00:00 ~ 07:00 에 접속하면 「오늘」(아직 안 열림)이 아니라 전날 결과를 보여 주는가 R-V2 · S19 결과 조회
Q9 문제은행 크기. 미출제 문제 전체를 내려주는가, 난이도별 일부만 내려주는가. 250만 명 × 평생 중복 금지를 버티는 문제 수 · 출제 고갈 시 동작 R-B3 · R-B6 · R-B7 응답 크기 · 문제 공급
Q10 그룹명 비교 규칙. 대소문자 · 공백 · 길이 · 허용 문자 R-G2 가입 검증
Q11 그룹 정원 10명의 기준. 07:00 이후 가입자(그날은 그룹원이 아님)도 정원에 세는가 R-G3 · R-G5 가입 거부 판정
Q12 미션 시작 전 유저의 실패 신호 · 07:00 이전 문제은행 요청의 응답 R-B1 · R-F2 오류 코드
Q13 진행도 -1 유저의 현황판 상태 표기. 유저에게 보이는 상태는 성공 · 실패 · 진행 중뿐인데, 접속하지 않은 유저를 「진행 중」으로 보이는가 §2 · §4.1 현황판 표시

12. 결정 기록

열린 질문을 닫은 결정. 원문과 어긋나는 결정은 그 사실과 우선한 원칙을 함께 적는다.

D1 · 2026-11-10 · 마감 직전 제출 가드 — 08:00 이전 제출자는 모두 인정한다

  • 결정: 네트워크 등의 이슈로 늦게 도착하더라도, 08:00 이전에 제출한 사람은 모두 성공 처리해야 한다는 원칙을 지키기 위해 가드를 둔다. 클라이언트는 클릭 이벤트 시각을 함께 보내고, 서버는 08:00 이후 3초 동안 도착한 신호 중 클릭 시각이 08:00 이전인 것만 승인한다.
  • 어뷰징 판단: 클릭 시각을 조작해 늦게 제출하는 어뷰징은 현실적으로 거의 없다고 본다. 얻는 것은 08:00 직후 최대 3초뿐이라 동기가 약하고, 손으로 파라미터를 고치려면 3초 넘게 걸린다.
  • 알고 택한 충돌: 「08:00:00 이후 서버에 도착한 풀이 신호는 어떤 경우에도 반영하지 않는다」(NFR-1)와 어긋난다. 이 점을 알고 위 원칙을 우선했다.
  • 귀결 [해석]: 그룹 마감 실패 확정은 유예가 끝난 08:00:03 (R-D3). 결과 화면 공개도 그 뒤다.
  • 닫은 질문: Q1 · Q2. 바뀐 곳: 세 줄 요약 · §3 · FR-6 · §5.6(R-D2~R-D4) · NFR-1.
  • 관련: 원문 「문제 출제 방식」 절의 「마감 직전 제출 가드」.
