HLD — deadline-result (마감 · 랭킹 · 결과 조회)

판 v3 · 2026-11-11 (v3: 처리 전 그룹은 「로딩 중」 — 요청이 확정하지 않음 · v2: 마감 확정 08:00 · 3번 진행 중 그룹만 08:00:03 · 랭킹 확정 08:00:03 · 그룹원 상태 5개 — prd D17) · 짝 문서: LLD · SPEC · ORACLE (아직 없음) · 근거: PRD v10 FR-6 · FR-7 · §5.6 · §5.9 · §6 · NFR-1 · NFR-2 · NFR-4 · D1 · D3 · D4 · D8 · D17 · 바탕: HLD platform

세 줄 요약

  • worker: deadline 은 08:00 에 돈다(1차). 「3번 문제 진입 · IN_PROGRESS」 그룹원이 없는 그룹은 바로 결과를 확정하고(끝내지 못한 그룹원은 FAILED), 있는 그룹은 08:00:03 까지 미룬다(화면 「로딩 중」). 08:00:03 에 다시 돌며(2차) 미룬 그룹을 확정하고 모든 그룹의 랭킹을 확정한다.
  • 08:00:00 ~ 08:00:03 의 유예 풀이 신호(클릭 08:00 전, D1)는 확정된 그룹에도 진행도 · 랭킹에 반영한다. 결과(성공/실패)는 1회 기록(NFR-2), 랭킹은 08:00:03 의 최종 상태(NFR-4).
  • 결과 조회는 「가장 최근에 확정된 결과」를 준다 — 오늘 확정됐으면 그룹 Hash 의 결과, 아니면 PostgreSQL 의 직전 게임 결과(D3). 미룬 그룹은 08:00:03 까지 PENDING.

1. 배경 · 목표

  • 맡는 요구: FR-6 · FR-7 · R-D1 ~ R-D5 · R-V1 ~ R-V5 · §6 랭킹 · NFR-1 · NFR-2 · NFR-4 · D1 · D3 · D4 · D8 · D17.
  • 목표
    • 08:00 에 미완료 그룹은 결과가 확정되고 화면이 결과로 넘어간다. 3번 문제를 푸는 중인 그룹원이 있는 그룹만 08:00:03 까지 기다린다.
    • 결과(성공 · 실패)는 정확히 한 번 기록된다. 랭킹은 08:00:03 에 확정되고, 그 뒤 어디서 보든 같다.
    • 같은 그룹의 랭킹은 어디서 계산해도(현황판 · 결과) 같은 규칙 · 같은 결과다.
  • 목표 아님: 풀이 신호의 시간 창 판정(solve-signal §3) · 전달(realtime-board).

2. 구성 요소

구성 요소 책임 의존
worker: deadline 08:00:00(1차) · 08:00:03(2차)에 버킷 1,024개를 나눠 그날 그룹 목록(day:{<b>}:<date>)을 돌며 Lua deadline 실행 Redis
Lua deadline 그룹 하나를 판정 · 확정(§3). 결과 · 랭킹을 그룹 Hash 에 쓰고 XADD · SPUBLISH Redis
랭킹 함수 (Lua 와 core 두 벌, 같은 규칙) §4 비교 함수. Lua 는 확정 · 스냅샷, core 는 현황판 만들기에서 쓴다 —
api BoardController GET /api/v1/games/results/latest BoardService
worker: persister 결과 · 랭킹 이벤트 → group_results · group_result_members 멱등 기록 LLD platform §3

3. 흐름

1차 · 08:00:00 — worker: deadline 이 그룹마다 Lua deadline(phase=1):

  1. 이미 결과가 있으면(08:00 전에 성공 · 즉시 실패) 건너뛴다.
  2. 「3번 진입 신호를 받았고(3번 지금 문제가 있음) 상태가 IN_PROGRESS」인 그룹원이 있으면 → 그룹 Hash 에 pending = 1, 결과는 쓰지 않는다. 그룹 상태 PENDING(화면 「로딩 중」)을 publish.
  3. 없으면 → NOT_STARTED · IN_PROGRESS 그룹원을 FAILED 로 바꾸고, HSETNX result FAILED_DEADLINE · 확정 시각 · 지금 상태의 랭킹(잠정)을 쓴다. 결과 이벤트(group.decided) XADD · publish.

유예 · 08:00:00 ~ 08:00:03 — solve-signal 이 D1 조건(클릭 08:00 전)을 통과한 풀이 신호를 반영한다.

  • 미룬 그룹: 그 3번 풀이로 그룹원 전원이 완료되면 solve-signal 의 그룹 판정이 결과(SUCCEEDED · FAILED_IMMEDIATE)를 확정한다.
  • 1차에 확정된 그룹: 진행도 · 마지막 풀이 도착 시각만 오른다. 상태(FAILED)와 결과는 그대로이고, 랭킹(잠정)을 다시 계산해 publish 한다.

2차 · 08:00:03 — worker: deadline 이 그룹마다 Lua deadline(phase=2):

  1. 결과가 없는 그룹(미룬 그룹 중 유예 안에 확정되지 않은 것) → 1차 3과 같이 확정(FAILED_DEADLINE).
  2. 모든 그룹의 랭킹을 지금 상태로 확정(rankingFinal = 1)하고 랭킹 확정 이벤트(group.ranking_final) XADD · publish.
  3. 이 뒤로 도착하는 풀이 신호는 모두 거부된다(solve-signal 시간 창).

처리 전 조회: worker: deadline 이 아직 그 그룹에 오지 않았으면(125만 그룹을 차례로 돈다) 결과 조회는 PENDING(화면 「로딩 중」)을 준다. 그 그룹이 처리되면 SSE group.result 로 결과가 간다 — 요청이 확정하지 않는다(사람 결정). 08:00:03 이 지나서야 처리되는 그룹은 1차 · 2차를 한 번에 한다(Lua deadline 이 TIME ≥ 08:00:03 이면 확정과 랭킹 확정을 함께).

결과 조회 GET /games/results/latest

  1. 오늘 그룹 Hash 에 result 가 있으면 → 그 결과와 랭킹(08:00:03 전이면 rankingFinal = false).
  2. 08:00 이후인데 오늘 그룹에 결과가 없으면(pending 이거나 worker: deadline 처리 전) → groupStatus: PENDING(화면 「로딩 중」).
  3. 그 밖(07:00 ~ 08:00 · 00:00 ~ 07:00) → PostgreSQL 에서 이 그룹의 가장 최근 결과(D3).
  4. 확정된 결과가 한 번도 없으면 → 404 NO_RESULT_YET. 1명 그룹은 미션을 시작할 수 없어 결과 데이터가 없으므로 여기에 해당한다(R-G6) — 탈퇴가 없어 오늘 1명 그룹은 지난날에도 1명 그룹이었다.
  5. 랭킹 항목의 상태는 SUCCEEDED · CHEAT_FAILED · FAILED — 화면에는 성공 · 실패(CHEAT_FAILED · FAILED 모두 「실패」, D4).

4. 랭킹 규칙 (PRD §6 을 비교 함수로)

두 그룹원 A · B 를 위에서부터 비교하고, 앞 키가 같을 때만 다음 키를 본다. | 순서 | 키 | 위로 가는 쪽 | |---|---|---| | 0 | 부정 실패(CHEAT_FAILED) | 아닌 쪽. 부정 실패끼리는 동률(여기서 끝) | | 1 | 진행도(-1 ~ 3) | 큰 쪽 | | 2 | (진행도 1~3) 마지막 풀이 도착 시각 | 이른 쪽(Redis TIME, 마이크로초) | | 3 | (진행도 1~3) 패스 | 안 쓴 쪽. 둘 다 썼으면 패스 번호가 큰 쪽 | | 2′ | (진행도 0) 지각(D8) | 지각 아닌 쪽 | | 3′ | (진행도 0) 패스 | 안 쓴 쪽. 둘 다 썼으면 동률(진행도 0 의 패스는 언제나 1번) | | — | (진행도 -1) | 동률 |

  • FAILED(마감 실패)는 랭킹 키가 아니다 — 진행도 그대로 비교한다(마감 실패자끼리도 많이 푼 쪽이 위).
  • 끝까지 같으면 동률. 순위 번호는 경쟁 순위(1, 1, 3) — 동률은 같은 번호, 다음 번호는 건너뛴다.
  • 같은 순위 안의 표시 순서는 로그인 아이디 사전순(화면을 고정하기 위한 것 — 순위 값에는 영향 없음).

5. 정합성 · 동시성

조건 보장 방식
NFR-1 · D1 풀이 판정의 시간 창은 Lua 의 Redis TIME 하나(solve-signal). 1차는 TIME ≥ 08:00:00, 2차는 TIME ≥ 08:00:03 일 때만 실행된다
NFR-2 1회 기록 결과는 HSETNX result 로만 쓴다(성공 · 즉시 실패 · 마감 실패 모두 같은 칸). worker: deadline · 신호 Lua · 요청이 동시에 와도 같은 슬롯의 Lua 라 한쪽만 쓴다. PostgreSQL 은 PK + ON CONFLICT DO NOTHING 으로 한 번 더
NFR-4 랭킹 일치 랭킹은 08:00:03 의 2차에서 확정해 스냅샷으로 남긴다. 그 뒤로 상태가 바뀌지 않으므로 결과 조회 · group.result · PostgreSQL 이 같은 값이다. 08:00:03 전의 랭킹은 「잠정」으로 표시한다
미룬 그룹 판정 「3번 지금 문제가 있고 IN_PROGRESS」는 Lua 안에서 그룹 Hash 로만 판정 — 서버가 아는 사실만 쓴다
worker: deadline 지연 처리 전 그룹은 PENDING(「로딩 중」) — 늦게 처리돼도 결과는 08:00 기준 상태로 같다(그 사이 상태를 바꾸는 신호는 유예 풀이뿐이고 그것은 정책상 반영 대상)

6. 결정과 버린 대안

결정 고른 것 버린 대안 근거
마감 확정 시각 08:00, 3번 진행 중 그룹만 08:00:03(D17) 모든 그룹 08:00:03 사람 결정. 대부분의 그룹은 08:00 에 결과를 본다. 늦은 3번 풀이로 성공할 수 있는 그룹만 기다린다
유예 신호와 확정 그룹 진행도 · 랭킹에 반영, 결과는 그대로 확정 그룹은 거부 사람 결정(D17) — 08:00 전에 클릭한 답은 모두 인정(D1)
랭킹 확정 08:00:03 의 2차 결과 확정 때 유예 신호가 랭킹을 바꿀 수 있다
확정 주체 worker: deadline 만 · 처리 전에는 「로딩 중」 요청 시 먼저 확정 · 키 만료(TTL) 이벤트 사람 결정. 확정 경로가 하나라 단순하다. 늦게 처리되는 그룹은 잠시 「로딩 중」
순위 번호 경쟁 순위(1, 1, 3) 조밀 순위(1, 1, 2) 「n명 중 몇 위」가 인원 수와 맞는다

7. 위험 · 열린 질문

  • worker: deadline 처리량: Lua 한 번 수십 µs × 125만 그룹을 1차 · 2차에 한 번씩 — 버킷을 나눠 병렬로 돌린다. 목표 완료 시간은 ORACLE 에서 정한다.
  • 랭킹 함수가 Lua 와 Kotlin 두 벌이다 — 같은 입력에 같은 순위를 내는지 ORACLE 이 같은 표(경계 사례)로 둘 다 검증한다.

8. 계약 초안과 다른 점 (docs/api/openapi.yaml · asyncapi.yaml v0.1 — SPEC 에서 반영)

  • 그룹 상태 PENDING(미룬 그룹 · 「로딩 중」)이 없다. 1명 그룹의 결과 조회는 NO_RESULT 가 아니라 404 NO_RESULT_YET 이다.
  • 결과의 rankingFinal(랭킹 확정 여부) · SSE group.ranking_final 이 없다.
  • 그룹원 상태가 NOT_STARTED · IN_PROGRESS · SUCCEEDED · CHEAT_FAILED · FAILED 다섯이다(D17). getLatestResult 설명의 「08:00:03 마감 확정」은 D17 로 바뀐다.
