PostgreSQL 은 LLD platform §2.1 의 users · groups · questions · served_questions · daily_progress 를 그대로 쓴다(스키마 변경 없음). 아래는 이 기능이 읽고 쓰는 Redis 키다. <b> = gid mod 1024, <date> = YYYY-MM-DD, <uid> = users.id, 시각 값은 모두 epoch 마이크로초 정수 문자열(Redis TIME 기준).

3. 처리 절차

공통: 인증 주체(auth-signup 이 정하는 access token 클레임 — 유저 PK · 로그인 아이디 · 그룹 PK)에서 uid · lid · gid 를 얻는다. 핫 경로(문제은행 · 진입 신호)는 PostgreSQL 을 읽지 않는다 — 명단이 아직 없거나 은행 캐시가 없을 때만 읽는다. 시각 판정은 Lua 안 TIME + offsetUs(= game.clock-offset) 이고, 앱 Clock 은 날짜와 경계 시각을 고르는 데만 쓴다.

3.1 게임 정보 GET /games/today

  1. now = clock.instant() + clockOffset. 게임 날짜 D = now 가 KST 로 그 날짜 08:00 전이면 그 날짜, 아니면 다음 날(SPEC GS1).
  2. now ≥ D 07:00 이면 명단 = RosterService.findOrCreate(gid, D)(§3.4). 그룹명 = 명단 #name, 그룹원 = 명단의 <uid> 필드 값.
  3. now < D 07:00 이면 명단을 만들지 않고 PostgreSQL 에서 지금까지의 07:00 이전 가입자를 읽는다(§6 Q4 — gid 하나, cutoff = D 07:00) · 그룹명(§6 Q6).
  4. 그룹원을 로그인 아이디 오름차순(문자 코드 순서 — 앱에서 정렬, DB 콜레이션에 맡기지 않는다)으로 정렬해 응답한다. startAt = D 07:00 · deadlineAt = D 08:00 · serverTime = now.

3.2 문제은행 = 미션 시작 POST /games/today/question-bank

    • OK sa created → 3 으로.
  3. 은행: GET bank:{<uid>}:<D>.
    • 있으면 그대로 쓴다(같은 날 재요청 = 같은 은행 — GS7).
    • 없으면: §6 Q2 로 출제 이력 → QuestionBankBuilder.build(catalog, served, 20)(§4.4). 한 난이도라도 0개 → QUESTIONS_EXHAUSTED(캐시에 넣지 않는다). 아니면 SET bank:{<uid>}:<D> <json> NX PX <D 08:00 − GameClock.now() ms>(§2.1). NX 가 실패하면(동시 요청이 먼저 넣음) 다시 GET 해 그 값을 쓴다 — 은행은 하나다(ORACLE I2). 그사이 키가 만료됐으면(08:00 직전) 방금 뽑은 은행을 그대로 준다.
  4. 내부 ID → catalog.byId 로 questionId(pk_hash) · 난이도 · 본문 · 분야 · 정답 해시를 채운다. 캐시에 없는 ID(문제 삭제 — 운영상 없음)는 건너뛴다.
  5. 응답: missionStartedAt = sa(µs → Instant, +09:00), 문제 목록(난이도 오름차순, 그 안은 은행 배열 순서).
  • 미션 시작(2)이 은행(3)보다 먼저다(HLD §3 순서) — 시작 시각에 은행 계산 시간이 끼지 않아 지각 판정이 공정하다. 그 대가로 QUESTIONS_EXHAUSTED 인 유저도 「시작」으로 남는다(§5).

  • 중간에 죽으면 같은 잡을 다시 돌린다 — 모든 단계가 멱등(IF NOT EXISTS · roster 없을 때만 · ON CONFLICT DO NOTHING). 그동안 요청은 §3.4 로 명단을 그 자리에서 만든다.
  • 실행 시각(v5.1): 루프가 GameClock.now()(시각 주입 포함) 다음에 오는 startAt(D) 까지 기다렸다가 run(D) 를 부른다. delay 는 단조 시계라 깨어나면 게임 시각으로 다시 보고, 아직이면 더 기다린다. run(D) 자체는 시각을 검사하지 않는다(부르는 쪽이 D 07:00 뒤에만 부른다 — 테스트는 직접 부른다).
  • 기동 · 재기동(v5.1): 기동하면 먼저 게임 시각의 오늘 · 내일 파티션을 만든다(DB now() 가 아니라 게임 시각 — 오프셋 실행에서도 그날 파티션이 있게). 그리고 startAt(오늘) ≤ now < deadlineAt(오늘)(07:00 ~ 08:00)이면 오늘 run 을 바로 한 번 돈다 — 07:00 실행 중 죽었다 다시 뜬 경우의 따라잡기. 08:00 이 지났으면 돌지 않는다(마감이 이미 그날 그룹 목록을 읽었다 — 늦게 올린 그룹은 결과 없이 남는다).
  • 실패(v5.2): 파티션 · 그룹 페이지 읽기 · 페이지 처리(명단 + Q10)는 3번까지(사이 retry-backoff 부터 두 배씩) 다시 한다. 파티션 · 페이지 읽기가 끝내 실패하면 그 실행이 예외로 끝나고, 페이지 처리가 끝내 실패하면 그 페이지를 건너뛰고 다음 페이지로 간다(요약의 failedPages). 루프는 실행이 예외 없이 · failedPages = 0 으로 끝날 때까지 그날 08:00 전까지 실행을 통째로 다시 돈다(사이 retry-backoff 부터 두 배 · 최대 30초 — 멱등이라 다시 돌아도 같다). 08:00 이 지나면 그만두고 ERROR member.gave-up 을 남긴다 — 그때까지 명단이 없는 그룹은 아무도 요청하지 않은 그룹이라 그날 결과가 없다. 07:00 의 짧은 DB · Redis 장애가 그날 확정을 통째로 건너뛰지 않게 한다. 같은 시각 파티션 생성이 api 기동과 겹쳐 「이미 있음」으로 실패해도 재시도에서 IF NOT EXISTS 로 지나간다.

  • 늦거나 일부 실패해도 정합성은 같다 — 요청 때 api 가 같은 함수로 만든다(§3.2-3). 07:00 이 지나도 끝나지 않은 06:50 실행은 계속 돈다(NX 라 api 가 만든 은행을 덮지 않는다).

  • Q12 는 바깥 SELECT 가 행을 내지 않으면 = 이번에 넣었다(Inserted) — inserted 칸은 읽지 않는다. 전제: 같은 (유저, 문제)를 다른 레인이 동시에 넣지 않는다 — 그룹 이동이 없고(R-G7) game.bucket-count 가 고정이라 한 유저의 이벤트는 평생 한 버킷 Stream 에서 차례로 처리된다. 이 전제가 깨지면(그룹 이동 · 버킷 수 변경) 바깥 SELECT 가 먼저 커밋된 행을 못 봐 Inserted 로 오판하고 운영 로그가 빠진다. 행이 나오고 (날짜, 번호)가 같으면 Replayed, 다르면 Duplicate → 운영 로그. 같은 메시지가 다시 오면(ACK 전 실패) 운영 로그도 다시 찍힌다 — at-least-once 의 대가로 받아들인다.
  • qid 는 Lua 가 문제 캐시로 확인한 questions.id 다. questions 에 없으면(캐시 · DB 불일치 — 손상) FK 위반으로 실패하고, 이는 칸 형식 오류가 아니라 재처리라 그 버킷이 persister.stuck 이 된다(solve-signal 의 없는 PK 와 같은 정책 — 문제는 지우지 않는 운영). PK 와 qid 를 대조하지는 않는다.
  • 출제 중복(Duplicate)이면 처음 기록(다른 날짜)을 그대로 두므로 「그날 그 번호에 이 문제를 고정했다」는 PostgreSQL 에 남지 않는다 — Redis 를 잃고 재적재(T-PF-5)하면 그 번호의 cur 를 되살릴 수 없다. 드문 운영 이상(D15)이라 받아들이고 재적재 일감에 넘긴다.

운영 로그(WARN 로그 줄 · 메시지가 한 줄 JSON · stdout): {"event":"question.served_duplicate","date":"<date>","loginId":"<lid>","questionNo":<no>,"questionId":"<pk>"}

4.2 start.lua — 미션 시작

입력 값

판정 순서(처음 걸리는 것으로 끝낸다):

4.3 shown.lua — 진입 신호

입력 값
KEYS [1] 그룹 Hash · [2] 명단 Hash · [3] ev:{<b>}
ARGV [1] uid · [2] questionNo · [3] questionId(pk) · [4] 내부 ID(qok=0 이면 빈 값) · [5] qok · [6] startUs · [7] deadlineUs · [8] offsetUs · [9] D · [10] gid

판정 순서:

  1. t < startUs → GAME_NOT_OPEN. t ≥ deadlineUs → SUBMISSION_CLOSED.
  2. 명단 없음 → NO_ROSTER. 그룹원 아님 → NOT_PARTICIPANT. #size = 1 → SOLO_GROUP.
  3. st = NOT_STARTED → MISSION_NOT_STARTED. st ∈ {SUCCEEDED, CHEAT_FAILED} → MISSION_ALREADY_FINISHED. (FAILED 는 08:00 이후에만 생겨 1 에서 걸린다 — 그래도 있으면 MISSION_ALREADY_FINISHED, fail.lua 와 같은 태도. 그 밖의 값 · 그룹원 칸 없음 · 진행도가 -1 ~ 3 의 정수가 아님은 스크립트 오류.)
  4. qok = 0 → QUESTION_MISMATCH(없는 PK · 난이도 ≠ 번호).
  5. questionNo ≠ p + 1 → QUESTION_OUT_OF_ORDER.
  6. cur = <uid>:cur
    • 비어 있고 (<uid>:pn, <uid>:pq) = (questionNo, pk) → QUESTION_MISMATCH(패스로 넘긴 문제 — 패스 앞 진입 신호의 늦은 재시도가 넘긴 문제를 되살리면 교체 문제가 막힌다 · SPEC GS11).
    • 비어 있음 → HSET <uid>:cur pk, XADD KEYS[3] * type question.shown date D gid <gid> uid <uid> lid <lid> version <지금 값> at t questionNo <no> questionId <pk> qid <내부 ID> shownAt t → {OK, p, st, 1}(필드 정본: HLD platform §4.2 — version 은 올리지 않은 지금 값).
    • cur = pk → 바꾸지 않고 {OK, p, st, 0}(멱등 — 이벤트 없음).
    • 그 밖 → QUESTION_MISMATCH(바꾸는 길은 패스뿐 — solve-signal).
  • 출력은 {ERR, code} · {NO_ROSTER} · {OK, p, st, created} 이고 칸은 모두 문자열이다(start 와 같음 — created 1 = 이번에 고정 · question.shown 1건).

4.4 은행 뽑기 (QuestionBankBuilder.build, Kotlin — Lua 아님)

입력: catalog.idsByDifficulty · 이 유저의 출제 이력 ID 집합 served · size = 20 · 난수(SecureRandom 이 아닌 ThreadLocalRandom — 보안 성질 불필요).

  1. 난이도 1 · 2 · 3 마다 후보 = idsByDifficulty[d] − served.
  2. 후보가 0 → 이 유저는 고갈(Exhausted).
  3. 후보 ≤ 20 → 전부(섞어서), 아니면 부분 Fisher–Yates 로 20개.
  4. 출력 BankDraw.Built(QuestionBank({1: […], 2: […], 3: […]})) · 고갈은 BankDraw.Exhausted(가장 낮은 고갈 난이도) — 고갈이면 은행을 만들지 않는다.
  • 버린 대안: SQL ORDER BY random() LIMIT 20(난이도마다 questions 전체 정렬 — 유저마다 3번 · 250만 명) 대신, 문제 ID 는 메모리에 있으므로 PostgreSQL 에는 출제 이력만 묻는다(PK 앞부분 user_id 로 인덱스 범위 조회).
