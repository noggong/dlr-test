1. 한 줄로: Lua 스크립트란

「Redis 안에서 여러 명령을 한 덩어리로, 중간에 아무도 끼어들지 못하게 실행하는 작은 프로그램」
  • Redis 는 명령을 한 줄로 하나씩 처리한다 (메인 스레드 1개).
  • Lua 스크립트는 여러 명령 + if 문을 묶어 한 명령처럼 실행한다 → 실행 중에는 다른 요청이 끼어들 수 없다(원자성).
  • 비유: 은행 창구 직원 1명. 보통은 손님이 「잔액 조회 → 줄 다시 서기 → 출금」을 하지만, 스크립트는 「조회하고 잔액 있으면 바로 출금」을 한 번에 창구에서 끝낸다.
  • 앱 ↔ Redis 왕복도 1번으로 줄어든다.

1-1. Lua 는 Redis 전용이 아니다

  • Lua = 다른 프로그램 안에 넣어 쓰도록 만든 작고 빠른 범용 스크립트 언어 (브라질 PUC-Rio, 1993~).
  • Redis 는 Lua 를 품고 있는 여러 프로그램 중 하나일 뿐이다.

게이트웨이 + Redis 조합 예시 (흔한 패턴): OpenResty · Kong 의 Lua 코드가 요청을 받아 → Redis 레이트 리미터 스크립트(EVALSHA)를 호출 → 한도 넘으면 앱 서버까지 가기 전에 429 로 끊는다.
→ 이 과제에서는 선택지일 뿐이다(07:00 스파이크 방어용). 핵심 자리는 Redis 스크립트(5장)다.

2. 동작 흐름 (그림)

  • 스크립트 캐시는 메모리에만 있다 → Redis 재시작 · 새 레플리카로 장애 전환 후엔 비어 있을 수 있다.
  • 그래서 클라이언트는 「EVALSHA → NOSCRIPT 면 EVAL」 패턴을 기본으로 쓴다 (대부분의 Redis 클라이언트 라이브러리가 자동 처리).

5. 이 과제에서의 활용 (플로우맵)

예시 스크립트 (설명용 · 실제 규칙은 PRD 기준으로 맞춘다)

-- KEYS[1]=progress KEYS[2]=rank KEYS[3]=done KEYS[4]=result
-- ARGV[1]=userId ARGV[2]=문제번호(1..3) ARGV[3]=nowMs ARGV[4]=deadlineMs ARGV[5]=그룹원 수
local user, n   = ARGV[1], tonumber(ARGV[2])
local now, dl   = tonumber(ARGV[3]), tonumber(ARGV[4])
local members   = tonumber(ARGV[5])

if now >= dl then return {'CLOSED'} end                       -- ❶ 마감 경계

local cur = tonumber(redis.call('HGET', KEYS[1], user) or '0')
if n <= cur then return {'DUP', cur} end                      -- ❷ 재시도 멱등
if n ~= cur + 1 then return {'OUT_OF_ORDER', cur} end

redis.call('HSET', KEYS[1], user, n)                           -- ❸ 진행도
-- 점수: 진행도 높을수록, 같은 진행도면 빨리 도달할수록 위 (ZREVRANGE 기준)
redis.call('ZADD', KEYS[2], n * 1e10 + (1e10 - (now % 1e10)), user)

local success = 0
if n == 3 then
  local done = redis.call('INCR', KEYS[3])                     -- ❹
  if done == members then
    if redis.call('SET', KEYS[4], now, 'NX') then success = 1 end  -- ❺ 정확히 1회
  end
end
return {'OK', n, success}
  • 시각(now)을 어디서 얻나 — ARGV 로 넘기면 테스트에서 시각 주입이 쉽다(가짜 시계). 대신 앱 서버들의 시계가 어긋나면 마감 판정이 흔들린다. redis.call('TIME') 은 Redis 서버 시계 하나라 기준이 하나로 모인다. → 면접 포인트: 「기준 시계를 무엇으로 했고 왜」.
  • 팬아웃(알림)은 스크립트 밖 — 스크립트 안에서 PUBLISH 도 되지만, 스크립트는 짧게 유지하고 반환값을 보고 앱이 보낸다.
  • 부동소수 점수 — ZSET 점수는 double(정확한 정수 약 2^53 까지). 진행도·시각을 한 숫자로 합칠 땐 자릿수가 넘치지 않게 범위를 계산한다.

7. 장점 / 단점

장점
  • 원자성: 락 없이 경쟁 상태 제거
  • 왕복 1번: 지연 감소 · 처리량 증가
  • 조건 분기 가능 (MULTI/EXEC 와 차이)
  • 재시도 루프 없음 (WATCH 낙관적 락과 차이)
  • 로직이 데이터 바로 옆에서 실행 → 앱 서버 수와 무관하게 결과 일관
  • 멱등 · 1회 판정을 코드 몇 줄로 표현
단점
  • 실행 중 Redis 전체가 멈춤 (긴 스크립트 = 전체 지연)
  • 롤백 없음: 중간에 오류 나면 그 전에 쓴 것은 남는다
  • 클러스터: 모든 키가 같은 슬롯이어야 함 → 키 설계 제약
  • 로직이 앱과 Redis 로 둘로 나뉨 → 테스트 · 디버깅 · 버전 관리 부담
  • Lua 를 아는 사람이 적음 (리뷰 어려움)
  • 스크립트 캐시는 휘발 → NOSCRIPT 처리 필요
롤백 없음 대응: 모든 검증(❶❷)을 먼저 하고 쓰기(❸~❺)는 맨 뒤에 몰아서 → 「검증 실패면 아무것도 안 쓴다」 구조.

8-2. CI/CD 파이프라인

  • 스크립트는 문자열로 코드에 박지 말고 .lua 파일로 → 리뷰 · 하이라이트 · lint 가능.
  • 테스트는 목(mock) 말고 진짜 Redis → 원자성은 진짜 Redis 에서만 검증된다.
  • 무중단 배포: 롤링 배포 중엔 구버전 · 신버전 앱이 같이 돈다 → 두 스크립트가 같은 키를 같은 의미로 다뤄야 한다(키 형식 바꾸면 새 키 이름으로).
  • 롤백: EVALSHA 방식은 앱을 되돌리면 스크립트도 같이 되돌아간다 (SHA 가 다르니 충돌 없음).

9. 퍼포먼스 — 느려지는 요인

핵심 한 줄: 스크립트가 도는 동안 Redis 전체가 그 스크립트만 한다. 그러니 「스크립트 1회 시간 × 초당 호출 수」가 곧 Redis 의 한계다.
#느려지는 요인왜대책
1루프 · O(N) 명령KEYS *, 큰 HGETALL · SMEMBERS · ZRANGE 0 -1키 수 · 원소 수를 작게 고정 (그룹 ≤ 10명이라 이 과제는 안전) · 카운터를 따로 둬서 전체 순회 대신 INCR
2동적 스크립트 생성값을 본문에 끼워 넣으면 매번 새 SHA → 컴파일 · 캐시 메모리 증가본문은 고정, 값은 항상 ARGV 로
3EVAL 로 본문 매번 전송네트워크 · 해시 계산 낭비EVALSHA (NOSCRIPT 시에만 EVAL)
4한 핫키에 몰림모든 요청이 같은 키(예: 전역 랭킹) → 클러스터여도 한 노드만 바쁨그룹 단위로 키 분산 ({d:g42}) — 이 과제는 그룹이 자연스러운 샤드
5큰 반환값응답 직렬화 · 네트워크 비용필요한 값만 반환
6크로스 슬롯클러스터에서 키가 다른 슬롯이면 CROSSSLOT 오류해시태그로 같은 슬롯에 · 안 되면 스크립트를 나눔
7Lua 테이블 생성 · GC큰 테이블을 만들면 메모리 할당 · 가비지 수집지역 변수 · 작은 테이블
8복제 · AOF스크립트가 쓴 명령들이 레플리카 · AOF 로 전파쓰기 명령 수 최소화 (Redis 7 은 「실제 바뀐 효과」만 복제)
9읽기 전용인데 마스터에서 실행마스터 부하 증가EVALSHA_RO / #!lua flags=no-writes 로 레플리카에서 실행
측정법: 부하 테스트(loadtest/) 중 INFO commandstats 의 usec_per_call 과 Redis CPU · p99 지연을 함께 본다. 짧은 스크립트는 보통 수~수십 µs 수준 — 실제 값은 이 과제의 부하 테스트로 확인한다.

10. 면접 설명 스크립트

30초 버전

「풀이 신호를 받으면 마감 확인 · 중복 확인 · 진행도 갱신 · 그룹 성공 판정을 해야 하는데, 같은 그룹 사람들이 동시에 풀면 앱에서 나눠 처리할 경우 성공이 두 번 기록될 수 있습니다. 그래서 이 네 단계를 Redis Lua 스크립트 하나로 묶어 원자적으로 실행했습니다. 락이 필요 없고 왕복도 한 번입니다. 키는 그룹 해시태그로 묶어 클러스터에서도 한 노드에서 돌게 했습니다.」

2분 버전 (뼈대)

  1. 문제: 동시 신호 · 재시도 · 08:00 경계 → 유실 · 중복 · 이중 판정 위험
  2. 선택지: RDB 트랜잭션(무거움) · MULTI/EXEC(분기 불가) · WATCH(경합 시 재시도 폭증) · Lua
  3. 선택 이유: 읽고-판단-쓰기 원자 · 왕복 1회 · 그룹 ≤10명이라 스크립트가 짧음
  4. 대가: Redis 를 막는다 → 스크립트를 O(1)~O(10) 으로 유지, 검증 먼저 쓰기 나중(롤백 없음 대응)
  5. 검증: 진짜 Redis 로 동시 신호 테스트 · 경계 시각 테스트 · 부하 테스트에서 usec_per_call 확인
  6. 운영: EVALSHA + NOSCRIPT 재시도, SLOWLOG · commandstats 모니터링

11. FAQ (예상 질문)

Q. MULTI/EXEC 로는 안 되나요?
  • MULTI/EXEC 는 명령을 묶어 한 번에 실행하지만 중간 결과를 보고 분기할 수 없다.
  • 「진행도를 읽고, 이미 풀었으면 무시」 같은 조건은 WATCH 를 걸고 실패 시 재시도해야 한다 → 같은 그룹에 동시 요청이 몰리면 재시도가 늘어난다.
Q. 스크립트 중간에 오류 나면 롤백되나요?
  • 안 된다. 이미 실행된 쓰기는 남는다.
  • 그래서 검증을 앞에, 쓰기를 뒤에 몰고, 입력 값은 스크립트 첫 부분에서 확인한다.
Q. 스크립트가 무한 루프면?
  • 기본 5초(busy-reply-threshold)가 넘으면 다른 클라이언트는 BUSY 오류를 받는다. 스크립트는 자동으로 멈추지 않는다.
  • 아직 쓰기 전이면 SCRIPT KILL, 이미 썼으면 SHUTDOWN NOSAVE 밖에 없다 → 그래서 루프 없는 짧은 스크립트로 만든다.
Q. Redis 클러스터에서도 되나요?
  • 된다. 단 스크립트가 쓰는 모든 키가 같은 슬롯이어야 한다.
  • 키 이름에 {그룹id} 해시태그를 넣어 같은 그룹 키를 한 노드에 모은다. 키는 반드시 KEYS 로 넘긴다(본문에서 키 이름을 만들어 쓰면 라우팅이 틀어진다).
Q. Redis 가 죽으면 진행도는요?
  • Lua 와 별개의 문제 — 영속화 설정(AOF appendfsync everysec 이면 최대 약 1초 유실 가능)과 레플리카 장애 전환이 결정한다.
  • 과제 요구 「재시작 후 진행 유지 · 허용 유실 명시」 → 이 값을 DESIGN 문서에 적는다. (어떤 설정을 쓸지는 아직 미결정)
Q. 시각은 앱에서 넘기나요, Redis TIME 을 쓰나요?
  • 앱에서 넘기면(ARGV) 테스트에서 가짜 시계를 쓰기 쉽다. 단 앱 서버 시계가 서로 다르면 경계가 흔들린다.
  • Redis TIME 은 기준이 하나다. 예전 Redis(스크립트 전체 복제 시절)에선 비결정 명령 뒤 쓰기가 막혔지만, 지금은 「효과 복제」라 가능하다.
  • 어느 쪽이든 「서버 도착 시각 하나를 기준으로 정했다」를 설명할 수 있으면 된다.
Q. Lua 스크립트가 느려지게 만드는 것은?
  • 루프 · 큰 컬렉션 순회 · 동적 스크립트 생성 · 한 키 쏠림 · 큰 반환값 (→ 9장 표).
Q. EVALSHA 는 왜 쓰나요? NOSCRIPT 는?
  • 본문 대신 40자 SHA 만 보내 네트워크를 아낀다.
  • 재시작 · 장애 전환 후 캐시가 비면 NOSCRIPT → 본문으로 EVAL 한 번 하면 다시 캐시된다.
Q. Functions 와 차이는?
  • Functions(Redis 7+)는 이름으로 부르고, 재시작 · 복제에도 남는다. 배포가 앱과 분리된다.
  • 작은 과제는 앱과 함께 배포되는 EVALSHA 가 단순하다.
Q. 스크립트 안에서 외부 호출(HTTP · 파일)은?
  • 불가. 샌드박스라 Redis 명령과 일부 라이브러리(cjson · cmsgpack · bit 등)만 쓴다. 전역 변수도 막혀 있다.
Q. 어떻게 테스트했나요?
  • 진짜 Redis 컨테이너에 같은 신호를 동시에 여러 번 → 진행도 · 성공 기록이 1번인지.
  • 마감 직전 · 직후 시각을 주입해 경계 확인.
  • 같은 요청 재시도 → 결과 동일(멱등).
Q. Lua 를 안 쓴다면 대안은?
  • RDB: UPDATE ... WHERE solved = n-1 (조건부 갱신) + 유니크 제약 → 정확하지만 스파이크 처리량이 문제.
  • 단일 명령으로 되는 것은 단일 명령으로: SET NX, HINCRBY, ZADD GT 등 — 스크립트 없이도 원자적.

12. 한 장 요약
