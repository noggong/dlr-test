**세 줄 요약**
- 매일 07:00~08:00 KST, 250만 명이 동시에 접속해 2~10명 그룹 단위로 각자 퀴즈 3문제를 순서대로 푼다. 그룹원 전원이 3문제를 풀면 그룹 성공. 08:00 에 제출이 잠기고 결과가 확정된다 — 3번 문제를 푸는 중인 그룹원이 있는 그룹만 08:00:03 까지 기다려 확정한다(D17).
- 서버는 문제를 고르거나 채점하지 않는다. 문제은행(정답은 해시)을 내려주고 **풀이 · 패스 · 부정 실패 신호**를 받아 진행도 · 그룹 상태 · 랭킹을 확정하고, 그룹원에게 실시간으로 알린다.
- 핵심 정합성은 마감 이후 미반영 · 성공 1회 기록 · 신호 유실/중복 없음 · 랭킹 일치 · 재시작 내구성이다. NFR-1 은 **마감 직전 제출 가드(D1)** 로 완화했다 — 08:00 이전에 클릭한 제출은 08:00:03 까지 도착하면 인정한다. 남은 충돌 · 빈칸은 §11 에서 결정한다.

## 1. 개요

| 항목 | 내용 |
|---|---|
| 제품 | 매일 같은 시각에 모든 유저가 동시에 접속해 그룹 미션을 수행하는 게임의 **백엔드** |
| 게임 시간 | 매일 **07:00 ~ 08:00 KST** (제한시간 1시간). 모든 시각은 KST(UTC+9) 기준 |
| 미션 | 그룹원 **각자** 퀴즈 3문제를 1번부터 순서대로 푼다. 그룹원 모두가 3문제를 다 푸는 순간 그룹 성공 |
| 퀴즈 컨셉 | KBS 「1 대 100」 같은 퀴즈쇼, 주관식. 분야: 시사 · 정치 · 사회 · 상식 |
| 서버의 몫 | 가입 · 인증 · 그룹, 문제은행 제공, 풀이/패스/실패 신호 반영, 그룹 판정, 실시간 전달, 마감, 결과 · 랭킹 |
| 클라이언트의 몫 | 문제 선정(무작위), 정답 판정(해시 비교), 로컬 스토리지 상태 유지, 부정행위 경고, 마감 시 제출 버튼 비활성화 |
| 범위 밖 | 클라이언트 · 관리자 화면, 결제, 보상 지급, 그룹 탈퇴와 이동 |

### 1.1 목표
- G1 일일 참가자 **250만 명**이 같은 시각에 접속하는 게임을 처리한다.
- G2 정합성 조건(§9.2)을 지킨다.
- G3 그룹원의 진행 상태가 다른 그룹원에게 **실시간**으로 보인다.
- G4 클라이언트 개발자가 개발 문서와 API 정의만으로, 서버 개발자에게 묻지 않고 개발을 시작할 수 있다.

## 2. 용어

| 용어 | 정의 |
|---|---|
| 진행도 | 유저가 그날 푼 문제 수 **0~3**. 줄어들지 않는다. 미션 시작 전(07:00 이전의 모든 유저 · 접속하지 않은 유저)은 **-1** — 현황판에는 0 으로 표기 |
| 미션 시작 | 그 날짜 **07:00 이후 문제은행을 한 번이라도 받은 것**. 07:30 에 처음 받으면 그때가 시작 |
| 풀이 신호 | 유저가 문제를 풀면 클라이언트가 보내는, 해당 문제 번호의 신호 (문제 번호 · 문제 PK · successTime · 클릭 시각) |
| 패스 신호 | 하루 1번, 지금 문제를 같은 난이도의 다른 문제로 바꿀 때 보내는 신호 (문제 번호 · 넘긴 문제 PK) |
| 실패 신호 | 로컬 스토리지가 빈 것을 감지한 클라이언트가 보내는 부정 실패 처리 요청 |
| 유저 미션 상태 | 그룹원 상태 5개(D17): `NOT_STARTED`(미접속 — 진행도 -1) · `IN_PROGRESS`(진행 중) · `SUCCEEDED`(3문제 완료) · `CHEAT_FAILED`(부정으로 실패 처리) · `FAILED`(시간 안에 끝내지 못함 — 마감 때 진행 중 · 미접속). `SUCCEEDED` · `CHEAT_FAILED` 는 「완료」(그룹 판정용). 화면 표기는 미접속 · 진행 중 · 성공 · 실패(`CHEAT_FAILED` · `FAILED` 모두 「실패」) |
| 그룹 상태 | **진행 중 · 성공 · 실패** |
| 그날의 그룹원 | 그 날짜 **06:50 전 가입자**까지만(결정 D24 — 원문은 07:00). 현황판 · 그룹 성공 조건 · 그룹 내 랭킹 · 그룹 인원 모두 이 기준 |
| 현황판 | 그날의 그룹원 목록. 그룹원마다 ID · 진행도(0~3) · 상태 · 랭킹을 보여 주고 랭킹순으로 정렬 |
| 지각 | 미션 시작 시각(07:00)보다 늦게 들어온 것 — 그날 첫 문제은행 요청의 서버 도착 시각이 **07:00:03 보다 늦으면** 지각(결정 D8). 서비스 상태가 아니라 **랭킹을 정할 때만** 쓴다 |
| 진입 신호 | 클라이언트가 문제 화면에 들어갈 때마다(패스로 바꾼 문제 포함) 보내는, 그 번호와 문제 PK 의 신호(결정 D6) |

## 4. 상태 모델

### 4.1 유저 (그날 기준)

| 상태 | 진행도 | 유저에게 보이는 상태 | 들어가는 조건 |
|---|---|---|---|
| 시작 전 (`NOT_STARTED`) | -1 (표기 0) | **미접속**(결정 D13) — 마감 확정 뒤에는 `FAILED`(D17) | 07:00 이전, 또는 그날 문제은행을 아직 받지 않음 |
| 진행 중 (`IN_PROGRESS`) | 0~2 | 진행 중 | 07:00 이후 문제은행을 처음 받음 |
| 완료 · 미션 성공 (`SUCCEEDED`) | 3 | 성공 | 3번 문제의 풀이 신호가 반영됨 |
| 완료 · 부정 실패 (`CHEAT_FAILED`) | 실패 처리 시점의 값 | 그룹 결과 확정 전 다른 그룹원에게는 **진행 중**(그 시점 진행도 · 순위 맨 아래 — D2), 본인에게는 **실패**. 그룹 결과 확정 뒤에는 모두에게 **실패** | 미션을 시작한 유저의 실패 신호(로컬 스토리지 빔)가 반영됨 |
| 마감 실패 (`FAILED`) | 마감 때의 값(08:00:03 까지 유예 신호로 오를 수 있다 — R-D5) | 실패 | 그룹 마감 확정(08:00 · 미룬 그룹은 08:00:03) 때 `NOT_STARTED` · `IN_PROGRESS` 였음(D17) |

- 진행도는 줄어들지 않는다. 완료된 유저의 상태는 바뀌지 않는다(성공 뒤 실패 신호는 무시 — D9).
- 자의로 중도 포기할 수 없다.

### 4.2 그룹 (그날 기준)

| 상태 | 조건 | 기록 |
|---|---|---|
| 진행 중 | 07:00 이후, 결과 미확정 | — |
| 성공 | 그날의 그룹원 **모두가 미션 성공**하는 순간 | 성공 판정과 완료 시각을 **정확히 한 번** 기록 |
| 실패 (즉시) | 그날의 그룹원이 **모두 완료**가 되는 순간, 미션 실패가 **한 명이라도** 있음 (전원 부정 실패도 같음) | 실패 확정도 **한 번만** 기록 |
| 실패 (마감) | **08:00** 에 아직 진행 중 — 단 「3번 문제 진입 · 진행 중」 그룹원이 있으면 **08:00:03** 에 판정(D17). 접속하지 않은 그룹원이 있으면 성공할 수 없어 여기로 온다 | 한 번만 기록 |
| 결과 없음 | 그날의 그룹원이 **1명** — 그룹이 아닌 것으로 취급, 미션을 시작할 수 없다 | 성공도 실패도 없음 |

- 성공 · 실패가 확정되는 즉시 그룹원 전원 화면에 결과 메시지와 그룹 내 랭킹을 보내고 결과 조회 화면으로 옮긴다.

## 5. 기능 요구사항

| id | 이름 | 요구 |
|---|---|---|
| FR-1 | 자동 참가 | 모든 유저는 매일 자기 그룹으로 게임에 자동 참가 |
| FR-2 | 그룹 소속 | 유저는 서비스를 쓰는 동안 계속 특정 그룹(2~10명)에 속함. 가입할 때 기존 그룹과 새 그룹 중 하나를 고름 |
| FR-3 | 게임 정보 조회 | 자기 그룹, 그룹원, 시작 및 마감 시각을 조회 |
| FR-4 | 풀이 신호 제출 | 푼 문제 번호의 풀이 신호를 보내 본인 진행도에 반영. 네트워크 재시도로 같은 요청이 여러 번 와도 **한 번만** 반영 |
| FR-5 | 실시간 진행 상태 | 그룹원 목록 · 각자 진행도(0~3) · 그룹 상태가 다른 그룹원에게 실시간으로 보임. 그룹이 성공하면 즉시 전원 화면에 성공 메시지와 그룹 내 랭킹. 전달 방식은 자유 |
| FR-6 | 마감 처리 | 08:00 이후 도착한 풀이 신호는 거부하고 미완료 그룹은 실패로 확정 — 단 마감 직전 제출 가드(D1)의 3초 유예는 예외 |
| FR-7 | 결과 조회 | 08:00 이 되면 모든 유저가 결과 화면을 봄. 성공/실패 여부와 그룹 내 랭킹(내 순위 포함) — 3번 문제를 푸는 중인 그룹원이 있는 그룹은 08:00:03 까지 「로딩 중」(D17) |
| FR-8 | 인증 | 보안상 문제가 없고 사용하는 프로토콜에 맞는 인증 체계. 가입 기능으로 가입하고 가입한 자격 증명으로 인증 |

### 5.1 가입 · 그룹 (FR-2 · FR-8)
- R-G1 가입할 때 **새 그룹**(그룹명을 지정) 또는 **기존 그룹**(그룹명을 입력) 중 하나를 고른다.
- R-G2 그룹명은 **유일**하다.
- R-G3 그룹이 10명으로 차 있으면 11번째부터는 「그룹이 꽉 찼다」고 알려 준다.
- R-G4 그 날짜 **06:50:00 KST 전에 가입한** 유저만 그날 게임에 참가한다. 06:50 부터 가입한 유저는 다음 날부터다(결정 D24 — 원문 해석은 07:00 이었다). 가입할 때 「06:50 이후 가입하면 오늘 미션에는 참여할 수 없다」고 안내한다 — 가입 응답의 `firstGameDate`(첫 참가 날짜).
- R-G5 그날의 그룹원 = 06:50 전 가입자(D24). 예: 2명 중 1명이 06:55 에 가입했으면 그날 그 그룹은 1명 그룹.
- R-G6 그날 그룹원이 **1명**인 그룹의 유저는 미션을 시작할 수 없고 「그룹원이 2명 이상이어야 미션을 시작할 수 있다」는 취지로 안내한다. 그날 결과(성공 · 실패)도 없다.
- R-G7 그룹 탈퇴 · 이동은 범위 밖이다.
- R-G8 한 계정은 한 곳에서만 로그인한다 — 살아 있는 refresh token 이 있으면 새 로그인을 거부한다. 인증은 JWT access token(1시간) + refresh token(2시간 · refresh 할 때마다 새로 발급)이고, 토큰은 로컬 스토리지가 아니라 쿠키에 둔다(결정 D16).

### 5.2 미션 시작 · 문제은행 (FR-1 · FR-3)
- R-B1 유저가 로그인하고 미션을 시작할 때 문제은행을 받는다. **07:00 이후 처음 받은 순간**이 그 유저의 그날 미션 시작이다(진행도 -1 → 0).
- R-B2 문제은행 항목: 문제 고유 PK(hash) · 난이도 · **정답 해시**. 실제 정답은 내려주지 않는다. 문제 본문과 분야도 함께 내려준다 [해석 — 클라이언트가 문제를 그려야 한다].
- R-B3 이 유저에게 **이미 낸 문제**(진입 신호로 화면에 나간 문제 — 맞힌 문제 · 패스로 넘긴 문제 · 못 푼 문제 모두, 결정 D6)는 빼고 내려준다. 난이도마다 미출제 문제 중 **20개**를 무작위로 내려준다(결정 D10). 같은 날 다시 받으면(R-B4) 같은 은행을 그대로 준다 — 그날 이미 낸 문제는 클라이언트가 뺀다(R-B6 · D18).
- R-B4 재접속하면 문제은행을 다시 받고, 클라이언트는 로컬 스토리지에 저장된 상태로 이어서 진행한다. 은행은 06:30 · 06:50 에 미리 만들어 둔 것을 주고, 없으면 그 자리에서 만든다(D18).
- R-B5 난이도는 1 · 2 · 3. 1번 문제 = 난이도 1, 2번 = 난이도 2, 3번 = 난이도 3.
- R-B6 문제가 노출될 때 클라이언트가 그 번호의 난이도에 맞는 문제 중 하나를 **무작위**로 고르고, 그 문제 화면에 들어가면서 **진입 신호**(번호 · 문제 PK)를 보낸다. 패스로 바꾼 문제도 같다(결정 D6). 클라이언트는 이미 화면에 낸 문제(넘긴 문제 포함)를 다시 고르지 않는다(결정 D15).
- R-B7 모든 문제는 모든 유저에게 **평생 단 한 번만** 제시한다(다음 날 이후에도 같은 문제 안 냄). 같은 그룹원끼리는 같은 문제가 나올 수 있다.

### 5.3 정답 판정 (클라이언트)
- R-A1 클라이언트가 유저 입력을 해시해서 내려받은 정답 해시와 비교한다.
- R-A2 정답과 유저 입력 모두 **띄어쓰기 전부 제거 → 소문자 변환 → 앞뒤 공백 제거** 후 해시한다(원문). 정확한 규칙은 결정 D22: ① 공백으로 보는 문자(D22 표 33개 — 탭 · 줄바꿈 · 전각 공백 · NBSP · 폭 0 문자 · 한글 채움 문자 포함)를 **어디에 있든 전부** 지운다(앞뒤 공백 제거는 여기서 끝난다) ② 유니코드 **NFC** ③ 영문 **A-Z 만** a-z. 해시 = `SHA-256(UTF-8("<문제 PK>:<정규화한 답>"))` 의 소문자 hex(결정 D7). 서버 · 클라이언트는 공유 테스트 벡터 `docs/api/answer-normalization-vectors.json` 으로 같은 결과를 확인한다.
- R-A3 서버 DB 에는 실제 정답과 정답 해시를 따로 저장하고, 클라이언트에는 해시만 내려준다.
- R-A4 틀리면 같은 문제를 다시 푼다(서버에 신호 없음).

### 5.4 풀이 신호 (FR-4)
- R-S1 풀이 신호에는 **문제 번호 · 문제 PK · successTime(맞힌 시각) · 클릭 이벤트 시각**을 싣는다. 패스 정보는 싣지 않는다.
- R-S2 서버는 문제 PK 로 이 유저에게 낸 문제를 기록해 평생 중복 금지(R-B7)를 지킨다.
- R-S3 같은 요청이 재시도로 여러 번 와도 진행도는 한 번만 오른다(NFR-3).
- R-S4 문제는 1번부터 순서대로 푼다 — 반영되는 신호의 문제 번호는 「현재 진행도 + 1」이다 [해석]. 이미 반영된 번호는 같은 결과로 응답하고, 건너뛴 번호는 거부한다 [해석].
- R-S5 랭킹의 「푼 시각」은 풀이 신호가 **서버에 도착한 시각**이다. successTime 은 클라이언트가 바꿔 보낼 수 있어 랭킹에 쓰지 않는다.
- R-S6 반영 즉시 그룹원에게 진행도를 전달하고(FR-5), 그룹 판정(§4.2)을 한다.

### 5.5 패스
- R-P1 하루 **1번**, 지금 문제를 같은 난이도의 다른 문제로 바꿔 받을 수 있다(재미 요소).
- R-P2 패스를 쓰면 클라이언트가 **그 즉시** 패스 API 를 호출해 문제 번호와 넘긴 문제의 PK 를 알린다. 그 번호를 끝내 못 풀어도 서버는 패스 사용 여부와 넘긴 문제를 안다.
- R-P3 넘긴 문제는 평생 중복 금지에 포함된다.
- R-P4 어느 문제 번호에서 패스를 썼는지가 랭킹에 반영된다(§6).
- R-P5 하루 2번째 패스는 거부한다 [해석].

### 5.6 마감 (FR-6 · NFR-1)
- R-D1 08:00 이 되면 클라이언트는 제출 버튼을 비활성화한다.
- R-D2 마감 직전 제출 가드: 클라이언트는 **클릭 이벤트 시각**을 파라미터로 보낸다. 서버는 08:00 이후 **3초 동안** 도착한 신호도 받되, 클릭 이벤트 시각이 08:00 이전인 것만 승인한다(네트워크 지연 대비). NFR-1 · FR-6 과 어긋나는 것을 알고 「08:00 이전 제출자는 모두 인정」 원칙을 우선해 택했다 — **결정 D1(§12)**.
- R-D3 **08:00** 에 `worker: deadline` 이 진행 중인 그룹을 판정한다. 「3번 문제 진입 신호를 받았고 상태가 `IN_PROGRESS`」인 그룹원이 한 명 이상인 그룹은 **08:00:03** 까지 판정을 미룬다(그동안 화면은 「로딩 중」) — 늦게 도착한 3번 풀이로 성공할 수 있기 때문이다. 그 밖의 그룹은 08:00 에 바로 실패로 확정하고, 끝내지 못한 그룹원(진행 중 · 미접속)은 `FAILED` 다(D17).
- R-D5 08:00 에 확정된 그룹에도 D1 유예(08:00:00~08:00:03 도착 · 클릭 08:00 전) 풀이 신호는 진행도 · 랭킹에 반영한다. 결과(실패)는 바뀌지 않는다 — 3번에 들어가지 않은 그룹원은 3번을 풀 수 없어 성공이 생기지 않는다. 랭킹은 08:00:03 에 확정한다(D17).
- R-D4 클릭 이벤트 시각은 클라이언트가 보내는 값이라 조작할 수 있지만, 그대로 믿는다 — 얻는 것이 08:00 직후 최대 3초뿐이라 동기가 약하고, 손으로 파라미터를 고치려면 3초 넘게 걸린다(D1). 랭킹은 여전히 서버 도착 시각으로 정한다(R-S5).

### 5.7 로컬 스토리지 · 부정 실패
- R-F1 새로고침이나 진행 상황에 따라 같은 문제로 돌아오기 위해 클라이언트는 로컬 스토리지를 쓴다.
- R-F2 그 날짜에 **미션을 시작한** 유저(진행도 0 이상)의 로컬 스토리지가 비어 있으면, 클라이언트가 서버의 **실패 처리 API** 를 호출한다. 서버는 그 유저를 그날 **미션 실패**로 처리하고 랭킹 · 그룹 판정에 반영한다. 클라이언트는 완료 화면 · 현황판으로 리다이렉트한다.
- R-F3 브라우저 닫기 · 탭 이동 · 속성 보기(로컬 스토리지를 지울 수 있는 곳) 시도에는 「부정행위로 실패 처리될 수 있다」 **경고만** 준다. 실제 실패 처리는 로컬 스토리지가 빈 경우뿐이다.
- R-F4 표시: **그룹 결과가 확정되기 전**에는 부정 실패 유저도 다른 그룹원에게 **실패 처리 시점까지 푼 문제 수와 「진행 중」**으로 보이고, 순위는 **맨 아래**다(결정 D2). 그룹 결과가 확정된 뒤에는 모두에게 **「실패」**로 보인다. 본인에게는 처음부터 「실패」다(R-F5).
- R-F5 실패 처리된 본인은 완료 화면으로 가서 현황판을 본다. 본인 상태는 「실패」이고 그룹 상태를 같이 본다.
- R-F6 부정 실패도 「완료」로 취급한다 — 나머지 그룹원이 모두 3문제를 풀면 그 즉시 그룹 **실패** 확정(§4.2).

### 5.8 실시간 진행 상태 (FR-5)
- R-R1 전달 대상: 그룹원 목록 · 각자 진행도(0~3, -1 은 0 으로) · 상태 · 그룹 상태.
- R-R2 1번 문제를 제출하면 바로 2번 문제로 가고, **같은 시점에** 다른 그룹원 현황판에 이 유저가 1번까지 풀었다고 표시된다.
- R-R3 그룹 결과(성공 · 즉시 실패 · 마감 실패)가 확정되면 그 즉시 전원 화면에 결과 메시지 + 그룹 내 랭킹을 보낸다.
- R-R4 재접속 · 늦은 접속(07:30)에는 다른 그룹원의 **현재** 진행도가 반영된 현황판을 준다.
- R-R5 전달 방식(WebSocket · SSE · 폴링 등)은 자유. 메시지 형식은 기계가 읽을 수 있게 정의한다(§9.3).

### 5.9 결과 조회 (FR-7)
- R-V1 그룹 결과가 확정되면(즉시 확정 · 08:00 마감 확정 · 08:00:03 미룬 확정) 모든 그룹원이 결과 화면을 본다: 성공 또는 실패 + 그룹 내 랭킹(내 순위 포함). 08:00 확정 그룹의 랭킹은 08:00:03 까지 유예 신호로 바뀔 수 있다(R-D5).
- R-V2 08:00 ~ 다음 게임 시작 전 접속: 직전 게임 결과와 다음 게임까지 남은 시간을 **둘 다** 보여 준다(미룬 그룹은 08:00:03 까지 「로딩 중」). 자정이 지나 00:00 ~ 07:00 이어도 **직전 게임(전날) 결과**다(결정 D3).
- R-V5 결과 화면에서 상태는 성공 · 실패 둘뿐이다 — 마감으로 실패한 그룹에서 3문제를 다 풀지 못한 그룹원도 **「실패」**로 보인다(결정 D4).
- R-V3 결과 화면의 랭킹은 최종 상태와 일치한다(NFR-4).
- R-V4 1명 그룹은 결과가 없다(R-G6).

## 6. 랭킹 규칙 (그룹 내)

위에서부터 차례로 비교한다. 앞 키가 같을 때만 다음 키를 본다.

| 순서 | 키 | 위로 가는 쪽 |
|---|---|---|
| 0 | 부정 실패 여부 | 부정 실패가 아닌 유저. **부정 실패 유저는 모두 꼴등으로 동률** |
| 1 | 진행도 | 큰 쪽 (3 → 2 → 1 → 0 → -1). 그래서 진행도 0 인 사람이 -1 인 사람(접속 안 함)보다 위 |
| 2 | (진행도 1~3) 그 문제를 푼 시각 | 먼저 푼 쪽. 시각 = 마지막으로 반영된 풀이 신호의 **서버 도착 시각** [해석: 「그 문제」 = 현재 진행도에 해당하는 문제] |
| 3 | (진행도 1~3) 패스 | 패스를 안 쓴 쪽. 둘 다 1회씩 썼으면 **높은 단계(문제 번호)**에서 쓴 쪽 |
| 2′ | (진행도 0) 지각 | 지각하지 않은 쪽(07:00 에 시작) |
| 3′ | (진행도 0) 패스 | 패스를 안 누른 쪽. 그래도 같으면 **동률** |
| — | (진행도 -1) | 서로 동률 [해석] |

- 지각 = 그날 첫 문제은행 요청의 서버 도착 시각이 07:00:03 보다 늦음(결정 D8).
- 진행도 -1 인 그룹원은 현황판에 「미접속」으로 보인다(결정 D13). 결과 화면에서는 「실패」다(D4).
- 그룹 결과 확정 전 실시간 현황판에서 부정 실패 유저는 다른 그룹원에게 「진행 중 · 실패 시점 진행도」로 보이되 순위는 맨 아래다(결정 D2 — §6 의 0순위 규칙을 확정 전에도 그대로 쓴다).

## 9. 비기능 요구사항

### 9.1 규모
- 일일 참가자 **2,500,000명**, 그룹 크기 2~10명.
- 리소스(DB · 컴퓨팅)는 합리적인 비용 범위에서 자유. 단 구조를 효율적으로 설계하지 않고 리소스만 늘려서 해결하지 않는다.
- 원문 숫자에서 바로 나오는 양 [해석 — 산술만, 실측 아님]:

| 양 | 값 | 계산 |
|---|---|---|
| 그룹 수 | 250,000 ~ 1,250,000 | 250만 ÷ 10 ~ 250만 ÷ 2 |
| 하루 최대 풀이 신호(재시도 제외) | 7,500,000 | 250만 × 3 |
| 하루 최대 패스 신호 | 2,500,000 | 250만 × 1 |
| 1시간 평균 풀이 신호 | 약 2,083 건/초 | 7,500,000 ÷ 3,600 — 07:00 직후 몰림은 평균보다 훨씬 크다(피크 배수는 확인 필요) |
| 동시 실시간 연결 | 최대 2,500,000 | 참가자 전원이 현황판을 켜 둔 경우 |

### 9.2 정합성 조건

| id | 이름 | 조건 |
|---|---|---|
| NFR-1 | 마감 이후 미반영 | **08:00:00 이후 서버에 도착한** 풀이 신호는 어떤 경우에도 반영되지 않는다 — **완화(D1)**: 판정은 서버 도착 시각으로 세 구간이다. ① 08:00:00 전 도착 → 반영(클릭 시각은 보지 않는다) ② 08:00:00 이상 08:00:03 미만 도착 → 클릭 시각이 08:00:00 전일 때만 반영 ③ 08:00:03 이상 도착 → 어떤 경우에도 반영하지 않는다 |
| NFR-2 | 성공 1회 기록 | 그룹의 성공 판정과 완료 시각은 **정확히 한 번** 기록된다 (실패 확정도 한 번 — §4.2) |
| NFR-3 | 유실 · 중복 없음 | 동시에 들어온 풀이 신호가 유실되거나 중복 반영되지 않는다 |
| NFR-4 | 랭킹 일치 | 결과 화면의 랭킹은 최종 상태와 일치한다 |
| NFR-5 | 재시작 내구성 | 서버 프로세스가 재시작돼도 진행 상태가 유지된다. 허용 가능한 유실 범위가 있으면 근거와 함께 명시한다 |

### 9.3 클라이언트 연동
- 클라이언트는 **모바일 앱과 웹** 양쪽.
- API 정의는 **OpenAPI** 처럼 기계가 읽을 수 있는 형식으로 제공하고, 실시간 전달 메시지 형식도 함께 정의한다.
- 개발 문서에는 **게임 하루 흐름에 따른 호출 순서**, **에러 코드와 클라이언트 대응 방법**을 담는다.
- 완료 조건: 클라이언트 개발자가 서버 개발자에게 따로 묻지 않아도 되는 수준.

## 10. 기술 제약과 자유도

- 언어 · 프로토콜 · 스토리지 · 미들웨어는 자유. 스토리지와 미들웨어는 **선택 이유와 포기한 대안**을 설계 문서에 적는다.
- 실행: **`docker compose up` 한 번**으로 서버와 의존 스토리지가 모두 떠야 한다. → 레포 루트 `compose.yaml` 이 `iac/compose.yaml` 을 include 해서 루트에서 한 번에 뜬다(README).
- 클라우드: 실제 클라우드 리소스는 쓰지 않는다. 운영 환경에서 무엇을 추가할지는 문서로만 설명한다.
- 범위 밖: 결제, 보상 지급 로직, 클라이언트 구현, 그룹 탈퇴와 이동.

## 12. 결정 기록

열린 질문을 닫은 결정. 원문과 어긋나는 결정은 그 사실과 우선한 원칙을 함께 적는다.

### D1 · 2026-11-10 · 마감 직전 제출 가드 — 08:00 이전 제출자는 모두 인정한다
- **결정**: 네트워크 등의 이슈로 늦게 도착하더라도, 08:00 이전에 제출한 사람은 모두 성공 처리해야 한다는 원칙을 지키기 위해 가드를 둔다. 클라이언트는 클릭 이벤트 시각을 함께 보내고, 서버는 08:00 이후 **3초 동안** 도착한 신호 중 클릭 시각이 08:00 이전인 것만 승인한다.
- **어뷰징 판단**: 클릭 시각을 조작해 늦게 제출하는 어뷰징은 현실적으로 거의 없다고 본다. 얻는 것은 08:00 직후 최대 3초뿐이라 동기가 약하고, 손으로 파라미터를 고치려면 3초 넘게 걸린다.
- **알고 택한 충돌**: 「08:00:00 이후 서버에 도착한 풀이 신호는 어떤 경우에도 반영하지 않는다」(NFR-1)와 어긋난다. 이 점을 알고 위 원칙을 우선했다.
- **귀결**: ~~그룹 마감 실패 확정은 08:00:03~~ → D17 이 바꿨다(마감 확정 08:00 · 3번 진행 중 그룹만 08:00:03).
- **닫은 질문**: Q1 · Q2. **바뀐 곳**: 세 줄 요약 · §3 · FR-6 · §5.6(R-D2~R-D4) · NFR-1.
- **관련**: 원문 「문제 출제 방식」 절의 「마감 직전 제출 가드」.

### D2 · 2026-11-11 · 그룹 결과 확정 전 부정 실패 유저 — 「진행 중」으로 보이되 순위는 맨 아래

### D20 · 2026-11-11 · persister 가 처리하지 못하는 메시지 — 3회 실패하면 PostgreSQL dead-letter 에 쌓고 넘어간다
- **질문**: `worker: persister` 가 처리하지 못하는 메시지(처리기 없는 `type` · 계속 실패하는 메시지)를 만나면 어떻게 할까? 지금은 그 버킷을 멈추고 ERROR 로그만 남긴다.
- **원문(사람 답)**: 「3회 실패하고 DLQ 와 같이 postgresql 에 쌓아줘 DLQ 처리프로세스는 이번 과제에서는 스펙아웃」
- **결정 [해석]**: 한 메시지가 3번 실패하면(처리기 없는 `type` 포함) 그 메시지를 PostgreSQL dead-letter 테이블에 한 행으로 쌓고 같은 흐름에서 ACK 해 버킷이 다음 메시지로 넘어간다 — 버킷이 서지 않는다. 쌓는 것: 버킷 · Stream id · `type` · 원본 칸 전체 · 실패 횟수 · 마지막 실패 사유 · 처음/마지막 실패 시각. 같은 (버킷, Stream id) 는 한 행이다(재처리에도 멱등). 횟수는 설정 `worker.persister.dead-letter-after`(기본 3).
- **메시지 잘못이 아닌 실패는 세지 않는다**: DB · Redis 연결 끊김 같은 일시 장애는 dead-letter 로 보내지 않고 지금처럼 backoff 뒤 다시 읽는다. dead-letter 쓰기 자체가 실패해도 ACK 하지 않는다 — 유실 금지(NFR-3).
- **다시 해도 안 되는 형식 오류**(`MalformedEventException`)는 3번을 기다리지 않고 처음 실패에서 dead-letter 로 보낸다 [해석] — 같은 칸을 다시 읽어도 결과가 같아 기다리면 버킷만 늦어진다(지금까지는 ERROR 로그만 남기고 버렸다).
- **범위 밖(spec-out)**: dead-letter 를 다시 넣는 처리 프로세스 — 재처리 · 조회 API · 운영 도구 · 경보 — 는 이번 과제에서 만들지 않는다. 쌓인 행은 운영자가 SQL 로 본다.
- **바뀐 곳**: platform HLD · LLD §2.1 · §3.1 · SPEC · ORACLE(O16 · O19 ~ O21) · 일감 T-PF-6.

### D21 · 2026-11-11 · 처리하지 못한 예외 — `INTERNAL_ERROR` 500 · `UNAVAILABLE` 503
- **결정**: 오류 코드에 `INTERNAL_ERROR`(500) · `UNAVAILABLE`(503)을 더해 **모든 오류 응답**을 `{ "code", "message" }` 형식으로 맞춘다. 지금까지는 처리하지 못한 예외(예: SSE 연결 때 Redis 구독 실패)에 Spring 기본 500 이 나가 본문이 이 형식이 아니었다.
- **나눔**: 의존 서비스(Redis · PostgreSQL) 장애 — 연결 실패 · 연결 끊김 · 명령 시간 초과 · 그룹 채널 구독 실패 — 는 503 `UNAVAILABLE`, 그 밖의 처리하지 못한 예외(서버 결함)는 500 `INTERNAL_ERROR`. 판별 목록은 LLD platform §4.1.
- **클라이언트 대응**: 503 은 잠시 뒤 다시 시도한다 — 신호 API 는 멱등이라 같은 본문으로, SSE 는 티켓을 이미 썼으므로 새 티켓으로(RB7 재연결 절차). 500 은 다시 시도하지 않고 「잠시 뒤 다시 열어 달라」고 안내한다.
- **노출 금지**: `message` 는 코드마다 정해진 문장뿐이다 — 스택 · SQL · 호스트 같은 내부 사정을 싣지 않는다. 서버는 원인을 ERROR 로그로 남긴다.
- **범위**: `api` · `realtime` 모두, 컨트롤러 밖(인증 WebFilter 등)에서 난 예외 포함. SSE 는 응답을 시작하기 전의 실패만 이 형식이다 — 200 을 낸 뒤 스트림 중 끊김은 realtime-board(T-RB-6)가 정한다.

### D22 · 2026-11-11 · 정답 정규화 — 공백 문자 전부 제거 → NFC → A-Z 만 소문자
- **질문**: R-A2(「띄어쓰기 전부 제거 → 소문자 변환 → 앞뒤 공백 제거」)가 **어느 문자까지**인지 정하지 않아, 클라이언트와 서버(시드의 `answer_hash`)가 다르게 구현하면 맞는 답이 틀린다(예: 전각 공백 · NBSP 를 지우는가, 터키어 `İ` 를 어떻게 소문자로 하는가, 한글 완성형과 첫가끝 자모 조합을 같게 보는가).
- **원문(사람 답, 2026-11-11)**: ① 「탭 · 전각 공백 포함 사람이 볼 때 공백이라고 인식할 만한 요소는 모두 제거」 ② 「소문자 변환은 영문 A-Z 만(언어 설정에 따라 결과가 달라지지 않게)」 ③ 「해시 전에 유니코드 NFC 로 맞춘다(한글 완성형/자모 조합 차이)」.
- **결정 — 처리 순서**: `normalize(답)` =
  1. 아래 표의 문자 33개를 **위치와 상관없이 전부** 지운다. 앞뒤 공백도 여기서 지워지므로 원문의 「앞뒤 공백 제거」는 따로 하지 않는다(결과가 같다).
  2. 유니코드 **NFC**(정준 결합). **NFKC 가 아니다** — 전각 영숫자 `ＡＢＣ` · 위 첨자 `²` · 호환 자모 `ㄱㅏ` 는 바뀌지 않는다. 바뀌는 것은 정준 분해가 있는 것뿐이다: 첫가끝 자모 U+1100 U+1161 U+11A8 → `각`(U+AC01), `A` + U+030A → `Å`, KELVIN SIGN U+212A → `K`.
  3. U+0041 ~ U+005A(A-Z)만 U+0061 ~ U+007A(a-z)로. 그 밖의 대문자(`İ` · `Å` · `Σ` · 전각 `Ａ`)는 그대로다. 언어 설정 소문자(Kotlin `lowercase()` · JS `toLowerCase()`)는 쓰지 않는다 — `İ` 가 `i̇`(i + U+0307)로 바뀌는 등 런타임 · 로캘마다 결과가 다를 수 있다.
  4. 해시 = `SHA-256(UTF-8("<문제 PK>:" + 결과))` 소문자 hex(D7). 결과가 빈 문자열이어도 해시한다(그 답을 받을지는 화면이 정한다).
- **공백으로 보는 문자 (33개)**:

| 묶음 | 코드 포인트 | 근거 |
|---|---|---|
| Unicode `White_Space` 속성 전부(25) | U+0009 ~ U+000D(탭 · LF · VT · FF · CR) · U+0020 · U+0085 · U+00A0(NBSP) · U+1680 · U+2000 ~ U+200A · U+2028 · U+2029 · U+202F · U+205F · U+3000(전각 공백) | 유니코드가 「공백」으로 정한 문자 전부 — 화면에 빈칸으로 보인다 |
| 폭 0 문자(5) | U+200B(ZWSP) · U+200C(ZWNJ) · U+200D(ZWJ) · U+2060(WORD JOINER) · U+FEFF(BOM · ZWNBSP) | 보이지 않는데 복사 · 붙여넣기로 섞여 들어온다. 사람 눈에는 「아무것도 없음」이라 남기면 맞는 답이 틀린다 |
| 예전 공백(1) | U+180E(MONGOLIAN VOWEL SEPARATOR) | Unicode 6.3 전까지 `White_Space` 였다 — 오래된 런타임 · 입력기와 결과를 맞춘다 |
| 한글 채움 문자(2) | U+3164(HANGUL FILLER) · U+FFA0(HALFWIDTH HANGUL FILLER) | 한글 자판에서 들어가는 「보이지 않는 빈칸」 |

  - **넣지 않은 것**: U+115F · U+1160(첫가끝 채움 — 자모 조합의 일부라 지우면 글자 조합이 바뀐다) · U+00AD(SOFT HYPHEN — 공백이 아니라 하이픈) · 문장 부호. 표 밖의 문자는 하나도 지우지 않는다.
- **순서를 이렇게 정한 근거**(실측 — `tools/answer_vectors.py` · Python `unicodedata` 14.0):
  - **지우기 → NFC** 다. NFC 를 먼저 하면 U+1100 + U+200B + U+1161 이 ZWSP 에 막혀 결합되지 않은 채 ZWSP 만 지워져 자모 둘(U+1100 U+1161)이 남는다 — 완성형 `가`(U+AC00)와 다르다. 지운 뒤 NFC 하면 `가` 다. 표의 문자는 모두 결합 등급 0 이고, NFC 로 표 밖 문자가 표 안 문자로 바뀌는 것은 U+2000 → U+2002 · U+2001 → U+2003 뿐이라(둘 다 표 안) 지우기를 앞에 두어도 정준 동치인 입력은 같은 결과가 된다.
  - **NFC → A-Z** 다. 소문자를 먼저 하면 `A` + U+030A 는 `å` 가 되고 완성형 `Å`(U+00C5)는 그대로라 같은 글자가 둘로 갈린다. NFC 를 먼저 하면 둘 다 `Å` 다.
  - 남는 차이(받아들임): NFC 뒤 A-Z 를 바꾸면 결합 문자가 붙은 6쌍(`T`+U+0308 · `W`/`Y`+U+030A · `J`+U+030C · `H`+U+0331 · `T`+U+0344)은 NFC 가 아닌 소문자 꼴이 되어 완성형 `ẗ` 등과 갈린다. A-Z 만 바꾸는 규칙의 범위 안이고 서버 · 클라이언트가 같은 함수를 쓰므로 판정은 어긋나지 않는다.
- **공유 테스트 벡터**: `docs/api/answer-normalization-vectors.json`(`vectors` = 입력 → 정규화 결과 → 해시 35줄 — 지우는 문자 33개를 모두 끼운 줄 포함, `seedQuestions` = 서버 시드의 실제 문제 4개의 문제 PK · 원래 정답 · 정규화한 답 · `answerHash` · 생성기 `tools/answer_vectors.py` — 기대값을 구현과 따로 계산하고 `--check` 를 docs CI 가 돌린다). 서버(`AnswerNormalizer` · 시드 SQL)와 클라이언트가 같은 파일로 테스트한다.
- **시드에 미치는 것**: 시드 답(`Mission <d>-<nnn> 정답`)은 ASCII 영숫자 · `-` · U+0020 · 한글 완성형만 써서 옛 규칙과 새 규칙의 결과가 같다 — 이미 적재된 `answer_hash` 는 바뀌지 않아 다시 적재하지 않아도 된다(LLD platform §2.2).
- **바뀐 곳**: R-A2 · platform LLD(§1 · §2.1 COMMENT · §2.2) · ORACLE(O14 · O34 · O35) · api-guide §3 · web-client SPEC(W19 — 연동 판 v5 에서 W16 → W19 로 합침) · LLD(§4) · `docs/api/openapi.yaml`(`answerHash`) · 일감 T-PF-11.

- **설정**: 기준 시각은 `game.join-cutoff`(기본 06:50). 기동 때 `join-cutoff ≤ prepare-times 의 마지막` 을 검사한다 — 어기면 은행을 미리 만들지 못한 참가자가 생긴다. 시각은 `GameClock`(시각 주입 `game.clock-offset` 포함) 기준이다.
- **06:50 이후 가입자의 그날**: 명단 밖 유저와 같다 — 문제은행 · 진입 · 풀이 · 패스 · 실패 신호 · 현황판은 `403 NOT_PARTICIPANT`, 게임 정보의 `group.members` 에 없다. 다음 날부터 참가한다. 정원(D12)에는 센다.

### D25 · 2026-11-11 · 로컬 데모 시계 · 시각 이동 API — `docker compose up` 하나로 사용자 테스트
- **사람의 요구(원문)**: 「서비스를 완벽히 테스트할 수 있는 환경을 쉘커맨드 하나로 구성한다. 해당 쉘커맨드는 docker compose up 으로 수행하도록 한다.」 고른 방향: 「데모 시계 + 시각 이동 API」.

- **결정**
  1. 로컬 compose 는 **데모 시계**를 켠다(`GAME_DEMO_ENABLED` — compose 기본 `true`, 앱 기본 `false`). 처음 뜬 앱이 「기동 `GAME_DEMO_LEAD`(기본 3분) 뒤 = 게임 07:00」이 되는 이동량을 정해 Redis 에 둔다. 이동량은 앞으로만(≥ 0)이고 06:50 가입 마감(D24)보다 10분 이상 앞서게 날짜를 고른다 — `users.joined_at` 은 DB `now()`(실제 시각)라, 방금 가입한 테스트 사용자도 그 게임의 참가자가 된다.
  2. **시각 이동 API**(`GET` · `POST /api/v1/dev/clock` — 데모 시계가 켜졌을 때만 라우트와 인증 예외가 있다). 게임 시각을 **앞으로만** 옮기고, 다음 경계(07:00 명단 확정 · 08:00 마감 · 08:00:03 랭킹 확정)의 5초 전까지만 허용한다 — 경계는 언제나 실제 시간이 흘러 지나가게 해 잡 · Lua 의 순서를 지킨다. 인증은 요구하지 않는다(로컬 전용 · 꺼지면 라우트가 없다 · curl 한 줄로 부른다).
  3. 세 앱(`api` · `realtime` · `worker`)은 Redis 의 같은 이동량을 1초마다 읽어 「지금」(`GameClock` · Lua `offsetUs`)에 더한다. `worker` 의 잡은 이동을 알아채면 기다림을 깨고 다음 실행 시각을 다시 고른다.
- **범위**: 로컬 데모 · 사용자 테스트 전용이다. 게임 규칙(§3 · §5)은 바뀌지 않는다. 운영 설정에서는 꺼져 있고 꺼진 앱은 Redis 키를 읽지도 않는다.
- **버린 대안**: 실제 시각을 바꾸는 컨테이너 시계(libfaketime) — PostgreSQL · Redis `TIME` 과 어긋난다. 이동량을 환경 변수로만 주기(지금의 `GAME_CLOCKOFFSET`) — 기동 때 고정돼 마감 · 결과를 보려면 다시 띄워야 한다. 뒤로 옮기기 — Redis 만료(`PX`)는 실제 시간으로 흐르고 그룹 `version` · 명단은 되돌릴 수 없어 어긋난다. 이동 API 에 인증 — 사용자 테스트의 한 줄 명령을 쿠키 다루기로 만들어 데모 목적을 해친다.

| 이름 | 범위 | 근거 | 문서 · 코드 현황 (2026-11-11) |
|---|---|---|---|
| `auth-signup` | 가입 · 그룹 선택/생성 · 로그인 · 인증 | FR-2 · FR-8 · §5.1 · D11 · D12 · D16 · D23 · D24 | HLD · 코드는 501 스켈레톤 |
| `game-session` | 게임 정보 조회 · 그날 그룹원 명단 · 미션 시작 · 문제은행 · 진입 신호 | FR-1 · FR-3 · §5.2 · D6 · D8 · D10 · D15 · D24 | HLD · 코드는 501 스켈레톤 |
| `solve-signal` | 풀이 신호 · 패스 신호 · 부정 실패 신호 · 그룹 판정 | FR-4 · §5.4~5.7 · NFR-2 · NFR-3 · D1 · D9 | HLD · 코드는 501 스켈레톤 |
| `realtime-board` | 실시간 현황판 · 결과 확정 알림 | FR-5 · §5.8 · D2 · D5 · D13 | HLD · 코드는 501 스켈레톤 |
| `deadline-result` | 마감 · 결과 조회 · 랭킹 | FR-6 · FR-7 · §5.6 · §5.9 · §6 · NFR-1 · NFR-4 · D1 · D3 · D4 · D8 | HLD · 코드는 501 스켈레톤 |
| `platform` | docker compose · 저장소 · 재시작 내구성 · 부하 · 로컬 데모 시계 | §9.1 · NFR-5 · §10 · D25 | HLD · LLD · SPEC · ORACLE · `iac/` 동작 |
| `web-client` | 데모 · 검증용 웹 클라이언트 — 디자인 시안 23개 상태를 퍼블리시하고 실제 API · SSE 에 연동했다(T-WC-*). 클라이언트 구현은 범위 밖이라 제출 판정 대상이 아니다 | §9.3 · G4 | HLD · LLD · SPEC · ORACLE · `frontend/` 구현 |

- 백엔드 기능 5개는 HLD 까지 있다. LLD · SPEC · ORACLE 은 아직 없고 하네스 H1 에 따라 **구현 전에** 써야 한다. 결정 D6 · D10 · D13 · D14 와 HLD 가 정한 것은 OpenAPI · AsyncAPI 초안(`docs/api/`, v0.1)에 아직 반영되지 않았다 — 각 기능 SPEC 을 쓸 때 반영한다(차이 목록은 각 HLD 의 「계약 초안과 다른 점」).
