+### 4.4 로컬 데모 시계 · 시각 이동 (prd D25 · T-PF-13)
+게임 시각 = 실제 시각 + `game.clock-offset`(기동 때 고정) + `shift`(런타임 이동량). `shift` 의 정본은 Redis 키 `demo:clock`(µs 십진 정수) 하나다. 설정 `game.demo.enabled=false`(앱 기본 — 운영)면 `DemoClockService` · `DevClockController` 빈이 없고 `shift` 는 0 이다 — 키를 읽지도 않는다.
+
+1. **첫 이동량** (`DemoClockRules.initialShift` — 빈 볼륨의 첫 기동). `r` = 실제 지금, `lead` = `game.demo.lead`(3분), `base` = `clock-offset`, `gap` = `start-time − join-cutoff`(10분).
+   `r` 의 KST 날짜부터 하루씩 늘려 가며 첫 `D` 를 고른다: `total = D 07:00 − (r + lead)` 가 `gap` 이상이고 `total − base ≥ 0`. `shift = total − base`.
+   - `total ≥ gap` 이면 게임 07:00 전에(실제 `D 07:00 − total` 전에) 가입한 유저의 `joined_at`(실제 시각)은 `D 06:50` 보다 앞이다 → 그날 명단(`joined_at < D 06:50` — prd D24)에 든다. `frontend/e2e/run.sh` 의 계산과 같은 규칙이다.
+   - `shift ≥ 0` 이라 게임 시각은 실제 시각보다 늘 앞이거나 같다(뒤로 가지 않는다).
+2. **세 앱이 같은 값을 쓰기** — 빈을 만들 때(모든 `SmartLifecycle.start` 전) `SET demo:clock <후보> NX` → `GET` → `shift` 에 반영. 먼저 쓴 앱의 값이 정본이고, 볼륨이 남아 있으면 그 값을 그대로 쓴다(재기동해도 게임 시각이 이어진다).
+   그 뒤 `game.demo.sync-interval`(1초)마다 `GET` 해 다르면 반영하고 `demo-clock.shifted from=… to=… now=…` INFO 로그를 남긴다. 읽기 실패는 WARN 로그 뒤 다음 주기에 다시 — 값은 그대로 둔다.
+   앱의 「지금」(`GameProperties.now(clock)` · `GameClock.now()`)과 Lua ARGV `offsetUs`(`GameProperties.clockOffsetUs`)는 같은 `shift` 를 읽는다. 앱끼리는 최대 `sync-interval` 만큼 늦게 맞춰진다.
+3. **시각 이동** (`DemoClockService.move` · `POST /api/v1/dev/clock`). `now` = 이 앱의 게임 지금, `target` = 옮길 게임 시각.
+   - 프리셋 `start` = `now` 뒤 가장 이른 07:00 − 10초, `deadline` = `now` 뒤 가장 이른 08:00 − 10초. 또는 절대 시각 `at`.
+   - `limit` = `now` 뒤 가장 이른 경계(그날 · 다음 날의 07:00 · 08:00 · 08:00:03) − `game.demo.move-margin`(5초). `now < target ≤ limit` 이 아니면 `409 CLOCK_MOVE_REJECTED`(SPEC §6.3).
+   - 통과하면 `new = shift + (target − now)` 를 `compareAndSet(읽은 값 → new)` 로 쓴다. 다른 요청이 먼저 바꿨으면(값이 다름) 한 번 다시 읽고 검사부터 다시 한다(두 번째도 지면 409). 쓴 앱은 자기 `shift` 를 바로 바꾸고, 다른 앱은 2의 주기에 따라온다.
+   - **왜 앞으로만 · 경계 앞까지만**: Redis 만료는 실제 시간(`PX` — 남은 ms)으로 흐르고, 그룹 Hash `version` · 명단 · `day:` 키 · 결과는 되돌릴 수 없다 — 뒤로 가면 이미 만든 명단 · 마감 결과 위에 같은 날이 다시 열린다. 경계를 건너뛰면 `worker` 의 07:00 명단과 08:00 마감이 늦게 · 동시에 돌아 순서(명단 → 마감 1차 → 2차)가 깨질 수 있다. 경계 5초 전까지만 옮기면 경계는 언제나 실제 시간이 흘러 지나가고, 5초는 다른 앱이 `sync-interval`(1초) 안에 따라오는 틈보다 넉넉하다. 06:30 · 06:50 `prepare-questions` 는 건너뛰어도 된다 — 지난 실행은 바로 돌고, 못 만든 은행은 `api` 가 요청 때 만든다(D18).
+   - 앞으로 옮기면 이미 쓴 Redis 키는 게임 시각으로 보면 그만큼 늦게 사라진다(만료가 늘어날 뿐 일찍 사라지지 않는다). 키에 날짜가 들어 있어 다음 게임과 섞이지 않는다.
+4. **잡의 다음 실행 시각 다시 고르기** — `worker: member`(07:00) · `prepare-questions`(06:30 · 06:50) · `deadline`(08:00 · 08:00:03)의 기다림은 `GameClock.pause(min(남은 시간, 원래 상한))` 이다. `pause` 는 `shift` 가 바뀌면 바로 돌아오고, 루프는 `GameClock.now()` 로 남은 시간을 다시 잰다 — 시각이 지났으면 곧바로 돈다. `prepare-questions` 는 원래 상한이 없어 남은 시간 전체를 기다렸는데, 이제 이동에도 깬다. 운영(꺼짐)에서는 `shift` 가 바뀌지 않아 기다림은 예전과 같다.
+5. **한계** — `users.joined_at` 은 실제 시각이라, 다음 날로 옮긴 뒤 가입한 유저의 가입 응답 `firstGameDate` 는 실제 날짜로 계산돼 게임 날짜보다 이를 수 있다(참가는 명단 규칙대로 된다). access · refresh 토큰의 만료(1 · 2시간)는 게임 시각으로 재므로 하루를 옮기면 다시 로그인한다. 브라우저는 서버 시각을 게임 정보를 받을 때 맞추므로 이동 뒤 새로고침한다.
+

+### D25 · 2026-11-11 · 로컬 데모 시계 · 시각 이동 API — `docker compose up` 하나로 사용자 테스트
+- **사람의 요구(원문)**: 「서비스를 완벽히 테스트할 수 있는 환경을 쉘커맨드 하나로 구성한다. 해당 쉘커맨드는 docker compose up 으로 수행하도록 한다.」 고른 방향: 「데모 시계 + 시각 이동 API」.
+- **문제**: 게임은 실제 07:00 ~ 08:00 KST 에만 열린다(마감 확정 08:00 · 랭킹 확정 08:00:03). 시각 주입은 기동 때 고정되는 `game.clock-offset` 뿐이라, 낮에 띄우면 미션 · 마감 · 결과를 테스트할 수 없다.
+- **결정**
+  1. 로컬 compose 는 **데모 시계**를 켠다(`GAME_DEMO_ENABLED` — compose 기본 `true`, 앱 기본 `false`). 처음 뜬 앱이 「기동 `GAME_DEMO_LEAD`(기본 3분) 뒤 = 게임 07:00」이 되는 이동량을 정해 Redis 에 둔다. 이동량은 앞으로만(≥ 0)이고 06:50 가입 마감(D24)보다 10분 이상 앞서게 날짜를 고른다 — `users.joined_at` 은 DB `now()`(실제 시각)라, 방금 가입한 테스트 사용자도 그 게임의 참가자가 된다.
+  2. **시각 이동 API**(`GET` · `POST /api/v1/dev/clock` — 데모 시계가 켜졌을 때만 라우트가 있다, 꺼지면 404). 게임 시각을 **앞으로만** 옮기고, 다음 경계(07:00 명단 확정 · 08:00 마감 · 08:00:03 랭킹 확정)의 5초 전까지만 허용한다 — 경계는 언제나 실제 시간이 흘러 지나가게 해 잡 · Lua 의 순서를 지킨다. 인증은 요구하지 않는다(로컬 전용 · 꺼지면 라우트가 없다 · curl 한 줄로 부른다).
+  3. 세 앱(`api` · `realtime` · `worker`)은 Redis 의 같은 이동량을 1초마다 읽어 「지금」(`GameClock` · Lua `offsetUs`)에 더한다. `worker` 의 잡은 이동을 알아채면 기다림을 깨고 다음 실행 시각을 다시 고른다.
+- **범위**: 로컬 데모 · 사용자 테스트 전용이다. 게임 규칙(§3 · §5)은 바뀌지 않는다. 운영 설정에서는 꺼져 있고 꺼진 앱은 Redis 키를 읽지도 않는다.
+- **버린 대안**: 실제 시각을 바꾸는 컨테이너 시계(libfaketime) — PostgreSQL · Redis `TIME` 과 어긋난다. 이동량을 환경 변수로만 주기(지금의 `GAME_CLOCKOFFSET`) — 기동 때 고정돼 마감 · 결과를 보려면 다시 띄워야 한다. 뒤로 옮기기 — Redis 만료(`PX`)는 실제 시간으로 흐르고 그룹 `version` · 명단은 되돌릴 수 없어 어긋난다. 이동 API 에 인증 — 사용자 테스트의 한 줄 명령을 쿠키 다루기로 만들어 데모 목적을 해친다.

+## 6. 로컬 데모 시계 · 시각 이동 (prd D25 · T-PF-13)
+게임은 07:00 ~ 08:00 KST 에만 열린다. 로컬 compose 는 **데모 시계**를 켜, 띄운 지 몇 분 뒤 게임이 열리고 시각 이동 API 로 마감 · 결과까지 바로 본다. 절차의 정본은 LLD §4.4.
+
+### 6.1 설정 (`game.demo.*`)
+| 설정 | 환경 변수 | 앱 기본 | compose | 뜻 |
+|---|---|---|---|---|
+| `game.demo.enabled` | `GAME_DEMO_ENABLED` | `false` | `true` | 데모 시계 · 시각 이동 API 켜기 |
+| `game.demo.lead` | `GAME_DEMO_LEAD` | `3m` | `3m` | 첫 기동 → 게임 07:00 의 실제 시간. 0 이상 · 1시간 이하 |
+| `game.demo.sync-interval` | — | `1s` | — | 세 앱이 Redis `demo:clock` 을 다시 읽는 주기. 0 보다 크다 |
+| `game.demo.move-margin` | — | `5s` | — | 시각 이동이 다음 경계에 다가갈 수 있는 한계. `sync-interval` 보다 커야 한다(기동 검사) |
+
+### 6.2 규칙
+| id | 규칙 |
+|---|---|
+| P9 | 꺼진 앱(운영 기본)은 런타임 이동량이 0 이고 Redis 키 `demo:clock` 을 읽지도 쓰지도 않는다. `GET` · `POST /api/v1/dev/clock` 은 라우트가 없어 404(Spring 기본 본문 — P5 의 예외) |
+| P10 | 첫 이동량: 빈 볼륨의 첫 기동 시각 `r` 에서 `r + lead` = 게임 `D 07:00` 이 되게 한다. `D` 는 이동 총량(`clock-offset` + 이동량)이 10분(`start-time − join-cutoff`) 이상이고 이동량이 0 이상인 가장 이른 날짜다 — 07:00 전에 가입한 테스트 사용자는 모두 `D` 의 그룹원이다(prd D24 · `joined_at` 은 실제 시각). 이미 키가 있으면(볼륨이 남음) 그 값을 쓴다 |
+| P11 | 세 앱은 같은 키를 읽는다. 시각 이동을 받은 `api` 는 바로, 다른 앱은 `sync-interval`(1초) 안에 따라온다 |
+| P12 | 시각 이동은 앞으로만, 그리고 `now` 뒤 가장 이른 경계(07:00 · 08:00 · 08:00:03) − `move-margin` 까지만이다. 경계는 실제 시간이 흘러 지나간다 |
+| P13 | `worker` 의 잡(07:00 명단 · 06:30 · 06:50 은행 · 08:00 · 08:00:03 마감)은 이동 뒤 `sync-interval` + 1초 안에 다음 실행 시각을 다시 고른다 — 시각이 지났으면 곧바로 돈다 |
+| P14 | 시각 이동 API 는 인증을 요구하지 않는다 — 로컬 전용이고 꺼지면 라우트가 없다(P9) |

+### 6.3 API (`x-app: api` · `x-demo-only: true` — openapi `dev` 태그)
+| 오퍼레이션 | 요청 | 응답 |
+|---|---|---|
+| `GET /api/v1/dev/clock` | 없음 | `200 DevClockResponse` |
+| `POST /api/v1/dev/clock` | `{ "to": "start" \| "deadline" }` 또는 `{ "at": "<ISO-8601 · 오프셋 필수>" }` — 둘 중 하나만 | `200 DevClockResponse`(옮긴 뒤) · `400 INVALID_REQUEST`(둘 다 · 둘 다 없음 · 모르는 `to` · 시각 모양) · `409 CLOCK_MOVE_REJECTED`(P12 위반 — 뒤로 · 경계 넘음) |
+
+`DevClockResponse`: `serverTime`(게임 지금) · `realTime`(실제 지금) · `shiftSeconds`(런타임 이동량, 소수 초) · `gameDate`(게임 정보 날짜 — GS1) · `startAt` · `deadlineAt` · `rankingFinalAt`(그 날짜의 07:00 · 08:00 · 08:00:03) · `moveLimit`(지금 옮길 수 있는 가장 늦은 시각 — P12). 시각은 모두 `+09:00`.
+
+```sh
+curl -s localhost:8080/api/v1/dev/clock                                                     # 지금 게임 시각
+curl -s -XPOST localhost:8080/api/v1/dev/clock -H 'Content-Type: application/json' -d '{"to":"deadline"}'   # 07:59:50 으로
+curl -s -XPOST localhost:8080/api/v1/dev/clock -H 'Content-Type: application/json' -d '{"to":"start"}'      # 다음 06:59:50 으로
+```
